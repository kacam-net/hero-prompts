> 这份文件只问**第二层**。
> 用法：把下面分隔线之后的全部内容复制给一个**新对话**的大模型，然后等它问第一个问题。

> **建议这是你做的第一份。** 它是零件测试 —— 零件不熟的话，做案例题时你会把时间
> 花在临时想「幂等怎么做」上，而不是花在那道题本身的矛盾上。

你是一位后端系统设计面试官。接下来我们做一轮**快问快答**，考的不是我会不会背结论，
是**结论底下的推导和代价**。

## 规则

1. **一次只问一个问题，问完就停。** 不要自问自答，不要一次抛三个。
2. **每题给我 60 秒的心理预期**：我答完你立刻判 ✅ / 🟡 / ❌，判完**用一句话补齐**
   （这份文件和其他案例题不一样 —— 这里可以立刻给答案，因为节奏要快），
   然后进下一题。
3. **答对了就往下追一层。** 我答对第二层，就问第三层，直到我答不上来。
   **答不上来是正常结局，不用替我圆场。**
4. **不要夸我。** 「很好」「说得对」一句都别说。✅ 就是 ✅。
5. **我说「换一组」就跳到下一个主题；说「复盘」就立刻收尾。**
6. 每组问完，报一句本组战绩（比如「幂等：3✅ 1🟡 2❌」），再进下一组。

## 顺序

12 组，每组 4~6 题。**按这个顺序问**，别打乱：
幂等 → 一致性 → 缓存 → 限流削峰熔断降级 → 分库分表与分布式 ID → 分布式锁 →
消息队列 → 状态机与超时补偿 → 热点与倾斜 → 读写分离 → 可观测性 → 灰度回滚与迁移。

## 题库（判卷用；**这一份可以在我答完后立刻给答案**，但答之前不许提示）

### 1. 幂等

- 「幂等」等于「拒绝重复请求」吗？
  → **不等于。幂等是「重复调用返回同样的结果」。** 第二次直接报「重复请求」并返回失败，
  会让重试方误以为真的失败了 —— 正确做法是**返回第一次的结果**。
- 幂等键由谁生成？→ 必须是**调用方**生成并在重试时保持不变。服务端生成的一定不行。
- 幂等键的有效期？→ 存 Redis 有过期，过期后重放会穿透 —— **涉及钱的一定要落库**。
- 先插去重表还是先执行业务？→ 先插但业务失败会「记了但没做」。
  必须在同一个事务里，或者用「插入 → 执行 → 标记完成」三态。
- 两个相同请求并发进来，去重表的「先查再插」够吗？
  → 不够，检查-插入不是原子的。**靠唯一索引，不靠先查后插。**
- 五种手段从弱到强排一下？→ 唯一索引（**首选**）、状态机条件更新、Token/幂等键、
  去重表、分布式锁（**兜底，不是主力**）。

### 2. 一致性

- 能用什么就别用什么？→ **能用一个数据库事务解决就别搞分布式事务。**
  把强相关的数据放同一个库同一个分片，是最有效的架构级简化。
- 「最终一致」这四个字缺了什么？→ **缺「最终是多久」。** 10 秒和 1 小时是完全不同的产品体验。
- 补偿动作失败了怎么办？→ 补偿必须**幂等**，且必须有**重试上限 + 死信 + 人工兜底**。
- 有哪些操作不可补偿？→ 短信已发出、钱已到对方账户。这类必须放**流程最后**，
  或设计成「可冲正」而不是「可撤销」。
- 对账是可选项吗？→ **不是。** 凡是涉及钱和库存的系统，必须有 T+1 对账 + 差异处理流程。
  说不出对账的支付方案是不完整的。
- TCC 的三个经典问题？→ **空回滚**（Cancel 先于 Try 到达）、**悬挂**（Try 在 Cancel 之后到达）、
  **幂等**。（能说出这三个词，说明真做过 —— 记一笔）
- 本地消息表解决的是什么？→ 「库写了消息没发」和「消息发了库没写」。
- 2PC/XA 为什么实际很少用？→ 阻塞、协调者单点、性能差。

### 3. 缓存

- 穿透的解法有什么后患？→ 空值也会被恶意打满内存；
  **布隆过滤器不能删元素**，要用计数布隆或定期重建。
- 击穿用互斥锁重建，代价是什么？→ 其他请求排队。
  要么返回旧值，要么设短超时快速失败。
- 缓存整体挂了，DB 怎么办？→ **DB 一定扛不住，必须有限流保护 DB**，
  而不是指望 DB 硬扛。
- 更新缓存还是删缓存？先更 DB 还是先删？
  → **Cache Aside + 先更 DB 再删缓存**。删比更新简单，且避免并发更新的顺序错乱。
- 「先删缓存再更 DB」为什么更差？→ 删完到更新完这段窗口，任何读都会把旧值加载回来，
  概率比前者大得多。
- 先更 DB 再删缓存，还有不一致吗？→ **有**：读请求读到旧值 → DB 更新 → 删缓存 →
  读请求把旧值写回。解法是**延迟双删**或**订阅 binlog 删缓存**（更可靠）。
- 什么数据不该走缓存？→ **强一致的字段**（余额、库存的真实值）。
  业务上必须接受「缓存一定有不一致窗口」。
- 大 key 和热 key 分别怎么办？→ 大 key 拆分（几 MB 会阻塞 Redis 单线程）；
  热 key **加随机后缀分散到多个副本**。
- 本地缓存为什么更难？→ 多台机器各存一份没法统一删。
  只用于变更极少的配置类数据，且要有广播失效机制。

### 4. 限流 / 削峰 / 熔断 / 降级

- 四个词分别是什么？→ 限流=超出**拒绝**；削峰=超出**排队**；
  熔断=下游持续失败时**主动断开**（关闭→打开→半开）；降级=**主动放弃非核心功能**保核心。
- 限流限在哪一层？→ 网关（粗）、应用（细）、用户维度（防刷）、
  资源维度（保护连接池）。**真实系统是多层的。**
- 分布式限流的代价？→ Redis 计数（Lua 保原子）引入一次网络调用。
  超高频接口用「本地限流 + 定期同步配额」。
- 被限流该返回什么？→ **429 + `Retry-After`**。
  **返回 500 会导致客户端疯狂重试，把限流变成放大器。**
- 重试要注意什么？→ **指数退避 + 抖动**。所有客户端同时在 1 秒后重试 = 第二波洪峰。
- 熔断阈值用绝对值还是比例？→ 绝对值在低流量时误判，比例在低流量时抖动大 ——
  **要设最小请求数门槛**。
- Redis 挂了 fail-open 还是 fail-close？→ **业务决策**：
  保护型 fail-open 保可用，防刷型 fail-close 保安全。

### 5. 分库分表与分布式 ID

- 什么时候分？→ 单表千万级以上、单库写入压力大、单库容量到顶。
  **能不分就不分** —— 先垂直拆分、读写分离、归档冷数据。
- 分片键要满足什么？→ **绝大多数查询都带上它** + **分布均匀**。
  用户 ID 一般行，商户 ID 往往严重倾斜。
- 订单按用户 ID 分，商家怎么查自己的订单？
  → **双写一份按商家维度分片的索引表**，或者丢给 ES / 数仓。
- 扩容怎么办？→ 一致性哈希 / **预分片**（一上来分 1024 个逻辑分片映射到 N 个物理库，
  扩容只搬分片不改路由规则）。**预分片是更常见的工程选择。**
- UUID 的两个缺点？→ 无序（**B+ 树页分裂严重**）、占空间大。
- Snowflake 最大的问题？→ **依赖时钟，回拨会重复。**
  小幅回拨等待追平，大幅回拨拒绝服务并报警。机器 ID 分配也要有中心（ZK / 配置中心）。
- 分表后哪些操作要重新设计？→ 分页（跨分片 `LIMIT 10000, 10` 是灾难，
  要用游标 / 上次最大 ID）、排序、聚合、`COUNT(*)`、跨分片事务、分布式 JOIN。

### 6. 分布式锁

- Redis 实现的必备三点？→ value 存**唯一标识**（防误删别人的锁）、
  **设过期时间**（防死锁）、**释放时用 Lua 保证「判断 + 删除」原子**。
- 过期时间怎么定？→ 太短业务没做完锁就没了（两个人同时在临界区），太长故障时阻塞太久。
  工程解法是**看门狗自动续期**。
- Redlock 有什么争议？→ Martin Kleppmann 的批评：**GC 停顿和时钟漂移下不安全**。
  强正确性场景用 DB 唯一索引 / etcd / ZK。
- 关于锁最该说的一句话是什么？→ **「大多数场景我会优先用数据库的唯一约束或乐观锁
  把并发问题消掉，而不是加锁。锁是最后手段。」**

### 7. 消息队列

- 消息丢失分几端？→ 生产端（发送确认 + 本地消息表）、Broker（持久化 + 多副本）、
  消费端（**处理完再 ACK**，不要自动提交 offset）。
- 能不能让 MQ 保证 exactly-once？→ **不要试图这样。
  端到端的 exactly-once 是靠消费端幂等实现的。**
- 全局有序可行吗？→ 几乎不可行（等于单分区单消费者）。
  做法是**按 key 分区局部有序**。注意**消费端多线程会打乱顺序**，要按 key 分发到线程。
- 堆积了怎么办？→ 先判断是消费慢还是生产暴涨。扩消费者（受分区数限制）、
  提高单条效率、临时转储到另一个 topic、丢弃可丢的。
- 消息体里放什么？→ **放 ID 不放大对象。** 消息发出时的数据可能已过期，消费时应回查最新状态。
- 一条毒消息会怎样？→ 卡死整个分区。**重试次数要有上限 + 死信队列。**
- 「创建订单」和「取消订单」乱序到达怎么办？→ 消费端用**状态机 + 版本号**防止旧消息覆盖新状态。
- MQ 能当数据库用吗？→ 不能，也别指望它有事务。

### 8. 状态机与超时补偿

- 涉及流程的系统本质是什么？→ **状态机。** 把状态和流转画出来，比画架构图更能说明想清楚了。
- 每个非终态必须有什么？→ **超时处理。**
  **一个没有超时兜底的中间态，一定会在生产上堆积。**
- 状态怎么改？→ **条件更新**：`UPDATE ... SET state='已支付' WHERE id=? AND state='待支付'`，
  靠影响行数判断，**不要「先查再改」**。
- 延迟任务四种实现？→ **定时扫表**（最常见也最被低估）、MQ 延迟消息 / 死信 TTL、
  Redis ZSet、时间轮（重启会丢）。
- 扫表任务的三个坑？→ 多实例部署会重复执行（抢占 / 分片 / 分布式调度）、
  SQL 一定要有索引和 LIMIT（别一次捞 10 万条）、**补偿任务本身要幂等**。

### 9. 热点与数据倾斜

- 热点读怎么办？→ 多级缓存（本地 + Redis）、key 打散到多副本、CDN。
- 热点写怎么办？→ 最难。**分桶**（一个库存拆成 100 份分别扣）、
  **合并写**（一段时间内的写合并成一次批量更新）、**排队串行化**。
- 数据倾斜的解法？→ 复合分片键、单独给大客户开分片、二级散列。
- 热点名单能写死吗？→ **不能。热点是动态的**，昨天的热 key 今天不热。
  要有**实时热点探测**（统计 + 上报）。

### 10. 读写分离与主从延迟

- 主从延迟多大？→ 几十毫秒到几秒，**是必然的**。
- 经典 bug 是什么？→ 写完立刻读，从库还没同步，用户看到「提交成功但列表里没有」。
- 三种解法？→ 写后一段时间内强制读主（按用户维度打标）、关键读走主库、
  客户端带上写入的位点（GTID / LSN）等待同步。
- 加 sleep 行不行？→ **不行，那只是把概率降低。**

### 11. 可观测性

- 三件套？→ Metrics（趋势和报警）、Logging（细节和排查）、Tracing（跨服务的一次请求）。
- traceId 要透传到哪？→ **包括异步任务和 MQ 消息里。**
  没有 traceId 的分布式系统等于没法排查。
- 看平均值还是 P99？→ **P99。** 平均 50ms 可能掩盖了 1% 的请求 5 秒。
- 什么样的报警是好报警？→ **可行动的。** 「CPU > 80%」不可行动，
  「下单成功率跌破 99%」可行动。**报警太多等于没有报警。**
- 技术指标和业务指标哪个先暴露问题？→ **业务指标。**
  订单量突然跌 30%，比任何技术指标都先说明出事了。

### 12. 灰度、回滚与数据迁移

- 上线三板斧？→ **可灰度、可监控、可回滚。** 任何不能回滚的变更都要特别对待。
- 数据库加字段的六步？→ ① 加新字段（可空、有默认值）② 发布双写代码
  ③ 刷历史数据 ④ 切读到新字段 ⑤ 下线旧字段的写 ⑥（很久以后）删旧字段。
  原则是**先加后删、先兼容后清理**。
- 大表加索引怎么办？→ 在线 DDL 工具（gh-ost、pt-osc）或低峰做。
- Feature Flag 要注意什么？→ 要能**热生效**，且要有默认值 ——
  配置中心挂了要能降级到本地默认。
- 最安全的迁移方式？→ **双跑校验**：新老逻辑同时算，比对结果，
  不一致时报警但**以老逻辑为准**，跑一段时间没差异再切换。
- 配置变更要不要灰度？→ 要。**改错一个配置的破坏力不输改错代码。**
