# 产品设计案例：引导式拆解

把 [product-design-playbook.md](../product-design-playbook.md) 拆成
**可以直接贴给大模型的提示词**。一个文件一道题，贴过去之后模型会当评审逐幕问你，
而不是把答案倒给你。

> **这批已经在站上了**：**[kacam.net/drills](https://kacam.net/drills)** ——
> 一键复制、直接跳转到 ChatGPT / Claude / DeepSeek / 豆包 / Kimi / Gemini，
> 还能记「这道题我练过」和写心得。这个目录是内容的源头。

## 和系统设计那批的关系

**结构一样，判据完全不同。**

[系统设计](../system-design-cases/)的约束是客观的（网络会超时、
一致性和可用性不可兼得），所以推导链相对确定，两个人推出来的答案会很像。

**产品设计的约束是人和钱** —— 用户的注意力有限、渠道有限、
团队的时间有限、钱要回本。这些约束同样固定，但它们**不指向唯一解**。
所以这批题**没有标准答案，只有立不立得住**，判据只有三条：

1. 你说得出这是谁的什么问题，**而且有证据**
2. 你说得出怎么算成功，**而且那个数字现在是多少**
3. 你说得出代价和你放弃了什么

**第三条最难伪装**，所以每一份的底牌里都有一栏专门写代价。

## 怎么用

1. 挑一道题，**新开一个空对话**（别在聊过这道题的对话里开）。
2. 把那个文件里 `---` 分隔线**之后**的全部内容复制过去。
3. 什么都别说，等它问第一个问题。
4. 中途四个口令：`跳过` ｜ `提示` ｜ `直说吧` ｜ `复盘`。
5. **末尾的底牌别自己先读。**

三条使用上的坑：

- **别急着给方案。** 这批题里有一多半的失分点在「还没问清楚就开始设计」。
- **准备好被追数字。**「效果会更好」「用户会喜欢」一律会被打断。
- **它开始夸你的时候，提醒它看铁律第五条。**

## 建议的路线

不要按编号刷。

1. **先做 [01](01-north-star.md)。** 「怎么算成功」是后面所有题的地基 ——
   不会定指标的人，做别的题时会一直在讨论方案而没有判据。
2. **然后按你眼下的事挑**：
   - 手上有一堆需求排不动 → `02`
   - 做了功能没人用 / 留存在掉 → `05` → `06`
   - 要定价或者要做冷启动 → `04` / `03`
   - 天天写需求文档 → **`10`，而且反复做**
3. **`08` 留到后面**，它是唯一一份「给你一份有问题的报告让你挑错」的，
   前面几份练过之后做才有意思。
4. **`10` 那一份最像日常工作**：第三幕十个异常路径，
   事先能想到几个，是这批题里最有信息量的一个数字。

## 为什么这么写（几个决定）

- **每一题都逼「怎么算成功」，而且必须在方案之前。**
  这是产品设计和系统设计骨架最大的不同 ——
  先有方案再凑指标，是这一行最普遍的坏习惯。
- **每一题都逼护栏指标。** 只有主指标的方案一定会被做歪
  （古德哈特定律），所以「这个指标会被怎么刷」几乎出现在每一份里。
- **两份用「给你一份有问题的材料」的形式**（`08` 的实验报告、
  `10` 的一句话需求）—— 因为这两件事在现实里就是以这个形式到你手上的。
- **底牌里都有「常见的错答」。** 产品设计没有标准答案，
  但**有明确的错答** —— 那一栏比「必答点」更有用。
- **不做「设计一个 XX App」这种题。** 那种题范围太大，
  底牌只能写成一套流程，挪到任何一道题上都成立（粒度判据见
  [drill-authoring.md](../drill-authoring.md) 第零步）。
