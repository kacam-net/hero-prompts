# 代码评审：给你一段埋了坑的代码

和 [system-design-cases/](../system-design-cases/) 同一个姿态（**拷问**：不许剧透、
不许夸、答不上来是正常结局），但材料反过来了：

**代码在提示词里，你不用带自己的。** 每一份都是一段几十行、看起来能跑的代码，
里面按严重度埋了十条左右的问题，**底牌就是那份问题清单**。

## 流程和别的系列不一样

固定五幕，第一幕的形状是这个系列独有的：

1. **先听你的。** 它把代码贴出来，然后闭嘴 —— 你自己读，把发现的问题一条条说完。
   **这一幕它一个字都不许提示。**
2. **逐条钉死。** 你说的每一条都要落到行号、时间线、后果的规模；
   报了不是缺陷的（命名、风格）当场记一次**误报**。
3. **它报你漏了什么**，从最严重的开始，一次一条，每条都问一句
   **「这条为什么你没看出来？是不知道这个问题存在，还是读的时候跳过去了？」**
4. **改一版**，只修问题不许顺手重构，然后逐条对。
5. 这类问题**怎么防**：评审拦得住哪些、拦不住哪些该靠什么。

收尾给的是一个数：**发现率 `自己找到 X / N（误报 Y）`**，
外加**漏掉的里有几条属于最严重的那一档**（会丢钱 / 会泄露数据 / 会把服务打挂）。
后面那个数比总分有用得多。

## 为什么值得练

评审是少数「**知道要看什么**比经验更管用」的活儿。同一段代码，
带着「并发下这两行之间会发生什么」这个问题去读，和顺着读一遍，看到的东西完全不同。
这批题给的就是那几个问题。

## 一条写题的约定

**代码要「看起来能跑、也确实跑得起来」**，不能是一眼假的教学样例 ——
一眼假的代码只能练「找茬」，练不了「读正常代码时保持警觉」。
所以每段里都有一半以上的行是正常的，埋的问题也**不集中在一处**。
