## 真相（**我说出来或者喊口令之前，一个字都不许透露**）

### 根因

今天 14:15 上线了一个新的「批量查订单」入口，
**给底层的查询语句加了一个 `WHERE order_id IN (...)` 的分支**。
调用方（一个内部对账系统）传进来的 id 列表**通常是几十个，但对大客户可能上万个**。

这个分支：

- 命中的是**极少数请求**（每分钟几十次，占总 QPS 的 2% 不到）
- 每次要走一遍全表扫（IN 列表太长，优化器放弃了索引）
- 单次耗时 3~8 秒

所以：**P99 被这 2% 拉爆，平均值几乎不动。**

### 你要按真相回答的观测结果

| 我问什么 | 你怎么答 |
| --- | --- |
| 平均 / P50 / P90 / P99 分别多少 | P50 35ms、P90 60ms、**P95 就开始翘（400ms）**、P99 3s |
| 按接口/路径拆 | 都是同一个接口路径 |
| **按调用方拆** | **有一个内部系统「对账中心」的 P99 是 6 秒，其余调用方都正常** |
| **按参数拆 / 慢请求的入参长什么样** | 慢的那些 `order_ids` 长度都在 5000 以上 |
| 慢查询日志 | 有，14:20 之后出现一批扫描行数几百万的查询，语句里是超长的 IN 列表 |
| 最近有没有发布 | **有两次**：14:15 订单服务发布（真凶），14:40 前端发布（无关） |
| CPU / 内存 | DB 的 CPU 从 30% 涨到 55%（**是结果不是原因**） |
| DB 连接数 | 从 40 涨到 90（**也是结果**：慢查询占着连接） |
| 主从延迟 | 有轻微延迟，2 秒左右（**伪线索**，是慢查询占资源导致的） |
| 缓存命中率 | 没变 |
| 网络 / GC / 机器负载 | 都正常 |
| 是不是所有机器都这样 | 是，12 台都一样 |

### 我埋的伪线索（收尾时要列出来）

1. **14:40 那次前端发布** —— 时间接近，但和后端无关。
   很多人一看到「有发布」就扑过去。
2. **DB CPU 和连接数上涨** —— 是慢查询的**结果**，不是原因。
   顺着它去查「是不是连接池不够」会浪费好几问。
3. **主从延迟** —— 同样是结果。
4. **「有用户反馈刷不出来」** —— 听起来像是所有人都受影响，
   实际上受影响的是一个内部系统。

### 最短路径（4 问）

1. **P50/P90/P95/P99 分别是多少？**（确认是长尾，不是整体变慢）
2. **按调用方（或者按租户/用户）拆一下 P99。**（找出那 2%）
3. **那些慢请求的入参长什么样？**（发现超长 IN 列表）
4. **14:20 前后有没有发布？改了什么？**（对上时间）

### 这一份要教会的（收尾时说出来）

**平均值和分位数背离的时候，问题一定在「某一类请求」上，不在「整个系统」上。**
这时候唯一有效的动作是**按维度拆**（调用方、租户、参数、机器、地域），
而不是继续看整体指标 —— 整体指标已经把答案平均掉了。

**还有一条：CPU、连接数、主从延迟这些「资源类」指标，
在故障里绝大多数时候是结果不是原因。** 先问「哪些请求慢」，
再问「为什么慢」，最后才轮到资源。
