## 真相（**我说出来或者喊口令之前，一个字都不许透露**）

### 根因

昨天 16:25，有人为了排查一个线上问题，
**在配置中心把这个服务的日志级别从 INFO 改成了 DEBUG，而且是全量生效**（不是灰度）。

推荐服务的热点路径上有一句
`log.debug("candidates: {}", JSON.toJSONString(candidateList))` ——
**这个 candidateList 每次有几千个对象**。DEBUG 打开之后：

- 每个请求都要做一次几千对象的 JSON 序列化（纯 CPU）
- 序列化出来的字符串几十 KB，还要写盘

于是 **CPU 全花在序列化和日志格式化上，业务逻辑本身一点没变** ——
这就是「QPS 没涨、功能正常、CPU 打满」的来源。

改配置的人排查完忘了改回去，而**配置变更不在发布记录里**，
所以「昨天没有发布」这句话是真的，也正是它把人带偏。

### 你要按真相回答的观测结果

| 我问什么 | 你怎么答 |
| --- | --- |

| 日志级别是什么 | **DEBUG** |
| 什么时候变成 DEBUG 的 | 昨天 16:25，配置中心上有一条变更记录，操作人是某某 |
| 有没有发布 | **没有代码发布**（配置变更不算在发布记录里） |

| 线程数、连接数 | 正常 |
| 下游依赖的耗时 | 正常 |
| 缓存命中率 | 正常 |

### 我埋的伪线索

1. **「昨天没有发布」** —— 真的没有代码发布，但**配置变更也是变更**。
   很多人一听「没发布」就转去查流量和依赖。
2. **Young GC 变频** —— 是结果不是原因；顺着它去调 GC 参数会白花好几问。
3. **iowait 有一点点** —— 会引人去查磁盘/网络，但 4% 说明不了什么。
4. **「所有机器都一样」** —— 容易被理解成「外部原因」（流量、依赖），
   其实它只是说明这是一个全局配置。

### 最短路径（3 问）

1. **CPU 里 user / sys / iowait 各占多少？**（78% user → 是在算东西，
   不是在等 IO，也不是在陷内核）
2. **火焰图上最宽的栈是什么？**（直接看到 JSON 序列化和日志）
3. **16:25 前后有没有任何变更 —— 包括配置？**（对上时间）

### 这一份要教会的

**「CPU 高」不等于「算得多」。** 第一步永远是把 CPU 拆成三份：

| 哪一份高 | 说明 | 往哪查 |
| --- | --- | --- |
| **user** | 真的在算 | 火焰图，找最宽的栈 |
| **sys** | 在陷内核 | 系统调用太多（小包 IO、频繁创建线程/进程、锁竞争进内核） |
| **iowait** | 在等 IO | 磁盘或网络，CPU 其实是闲的 |

**拆完再看火焰图，看完再猜原因** —— 顺序反过来（先猜「是不是 GC / 是不是死循环」）
是这类问题上最常见的时间浪费。

**还有一条要记住：「没有发布」不等于「没有变更」。**
配置中心、开关、灰度规则、DNS、证书、上游的流量策略、
下游的限流阈值 —— 这些都能在没有一行代码变化的情况下改变系统行为，
而且**多数公司的「发布记录」不覆盖它们**。
问变更的时候要问全：**「有没有任何东西变过，包括配置？」**
