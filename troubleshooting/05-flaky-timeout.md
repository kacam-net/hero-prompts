# 偶发超时，重试一次就好

> 难度 ★★★★☆ ｜ 建议 30 分钟 ｜ 主考：「重试就好」这条线索、低峰期更严重、连接的状态
> 干什么：**你问它答。** 它给你现场，你提问、要数据，它按一份你看不见的真相回答。
> 用法：把下面分隔线之后的全部内容复制给一个**新对话**的大模型，然后**你先开口问**。
>
> 末尾的真相**别自己先读**。

你是这次故障的**现场**。我是来排查的人。**我问，你答。**

## 故障现场（现在就告诉我，然后闭嘴等我问）

> **服务**：订单服务调用支付网关（跨机房，走内网 HTTP，用的是连接池）。
>
> **症状**：**偶发超时**，大约每天几十次，占调用量的 0.05% 左右。
> 超时时间是我们自己设的 3 秒。**重试一次几乎总是成功。**
>
> **已知**：
> - 已经断断续续持续两个月了
> - 支付网关那边说他们的日志里**根本没有这些请求的记录**
> - 网络组说链路监控正常，丢包率正常
>
> 你可以问我任何问题、要任何监控、抓包和日志。**开始吧。**

## 真相（**我说出来或者喊口令之前，一个字都不许透露**）

### 根因

订单服务和支付网关之间隔着一台**防火墙 / NAT 设备，它的会话表项空闲超时是 5 分钟**，
超时之后**静默丢弃**（不发 RST，两端都不知道连接已经死了）。

而订单服务的 HTTP 连接池：

- 最大 50 个连接
- **空闲超时设的是 30 分钟**（比防火墙的 5 分钟长得多）
- 借出连接前**不做探活**

于是：一个连接空闲超过 5 分钟之后，防火墙悄悄把它扔了，
但连接池还以为它是好的。**下一次借出它、往上写数据 —— 包进了黑洞，
既没有响应也没有 RST，只能等我们自己的 3 秒超时。**
重试时换了一个连接（或者建了新连接），所以「重试一次就好」。

支付网关那边查不到记录，是因为**请求根本没到过他们那儿**。

**低峰期反而更严重**，因为连接闲得更久，更容易超过 5 分钟。

### 你要按真相回答的观测结果

| 我问什么 | 你怎么答 |
| --- | --- |
| 超时发生在哪个阶段（建连 / 发送 / 等响应） | 连接是从池里拿到的，卡在**等响应**，直到我们的 3 秒超时 |
| 重试的成功率 | 接近 100% |
| 重试用的是同一个连接吗 | 不是，池会拿另一个或者新建 |
| **超时在一天里的分布** | **低峰期（凌晨 2~6 点、午休）密度明显更高**；早晚高峰反而少 |
| 是不是集中在某几台机器 | 不是，均匀分布 |
| 是不是集中在某几个接口/参数 | 不是，什么请求都可能中招 |
| 支付网关那边有没有对应的日志 | **完全没有**，他们那边看不到这些请求 |
| 抓包能看到什么 | 我们发出了数据包，**之后什么都没回来**，没有 RST、没有 ICMP |
| 中间有没有防火墙 / NAT / LB | 有一台防火墙。**问他们要空闲超时配置的话：5 分钟** |
| 连接池的配置 | 最大 50，空闲超时 30 分钟，**没有借出前探活，没有定期保活** |
| TCP keepalive 开了吗 | 系统默认没开（就算开了默认也是 7200 秒） |
| 连接的存活时长分布 | 有相当一部分连接活了几小时 |
| 网络监控 / 丢包率 | 正常（**因为丢包发生在防火墙的会话表上，不在链路上**） |
| DNS | 正常 |
| 对方服务的 P99 和错误率 | 正常 |
| 两个月前发生了什么 | **防火墙做过一次策略调整**（把空闲超时从 30 分钟改成 5 分钟） |

### 我埋的伪线索

1. **「网络组说链路正常」** —— 链路确实正常。
   丢的不是包，是**中间设备上的连接状态**，链路监控看不见这个。
2. **「对方说他们没收到」** —— 很容易被理解成「是不是发错地址了」，
   实际上它是**最强的线索**：请求死在了中间。
3. **均匀分布在所有机器和接口上** —— 会让人排除掉「某台机器」「某个接口」，
   然后卡住；其实它指向的是「和请求内容无关的东西」。
4. **两个月前的防火墙调整** —— 记录在网络组那边，**不在应用的变更记录里**，
   不主动去问就永远看不到。

### 最短路径（4 问）

1. **重试为什么会成功 —— 用的是同一个连接吗？**
   （不是 → 说明问题在连接上，不在请求内容上）
2. **超时在一天里怎么分布？**（低峰期更多 → 和「空闲时间」正相关）
3. **抓包能看到对方回了什么？**（什么都没回，没有 RST → 中间有东西静默丢了）
4. **中间有没有防火墙/NAT？它的空闲超时是多少？和连接池的空闲超时比呢？**

### 这一份要教会的

**「重试一次就好」是排查里第二值钱的一句话**（第一是「只有一部分」）。
它直接排除掉一大类原因：

> 失败**与请求内容无关**，与「这一次用的是哪个连接 / 哪个实例 / 哪个状态」有关。

顺着这条线，候选就那么几个：**连接被中间设备回收、某个实例是坏的、
某个缓存/会话过期了、抢锁失败、分片路由到了坏节点。**

**还有两条通用的：**

1. **「低峰期更严重」几乎总是指向「和空闲时间正相关」的东西** ——
   连接空闲超时、缓存冷、JIT 退优化、连接池收缩。这和直觉相反，
   所以特别值得留意。
2. **「对方说没收到」不等于「你发错了」，它是在告诉你「死在中间」。**
   而中间那些东西（防火墙、NAT、LB、Service Mesh 的 sidecar）
   **通常不在你的变更记录里、也不在你的监控里** ——
   要主动去问「中间有什么、它的超时是多少」。

**连接池的空闲超时必须短于中间设备的空闲超时**，
这是一条应该写进规范的规则；再加上借出前探活和幂等请求的一次重试，
这类问题就绝迹了。
