## 真相（**我说出来或者喊口令之前，一个字都不许透露**）

### 根因

**不是内存泄漏，是一个没有上限的本地缓存。**

三个月前有人为了「减少 Redis 调用」，在代码里加了一个
`private static final Map<Long, UserActivityState> CACHE = new HashMap<>();`，
**key 是用户 id，从来不清、没有容量上限、没有过期**。

活动服务每周会被几百万个不同用户访问，所以这个 Map 只增不减 ——
**每个条目不大（约 300 字节），但一周积累几百万个就是 1~2GB。**

它在功能上完全正确（缓存命中率还挺高），所以没有任何报错，
业务指标也一切正常。**这就是它藏了两个月的原因。**

### 你要按真相回答的观测结果

| 我问什么 | 你怎么答 |
| --- | --- |
| 涨的是堆内还是堆外 | **堆内**。RSS 和堆用量同步涨，堆外（Metaspace、直接内存）平稳 |
| GC 日志长什么样 | Young GC 正常回收，**每次 Full GC 之后老年代的存活对象都比上一次多**（阶梯式上涨） |
| 老年代的对象直方图（histogram） | 排第一的是 `java.util.HashMap$Node`（约 400 万个），

| 那些对象的**持有链**（GC root 到它的路径） | 一个 `com.xx.activity.StateHolder` 的 static 字段 `CACHE` |
| 这个 CACHE 是什么时候加的 | 三个月前的一次提交，注释写着「减少 Redis 调用」 |
| 它有过期或者容量上限吗 | 没有 |
| 一周有多少不同用户访问 | 三百到五百万 |
| 有没有用第三方缓存库 | 没有，就是裸 `HashMap` |
| 线程数 / 连接数 | 正常，没有增长 |

### 我埋的伪线索

1. **「重启就好」** —— 容易让人直接归为「泄漏」，
   于是一头扎进「找哪个对象没释放」，而漏掉「缓存没上限」这个可能。
2. **有一处 `ThreadLocal`** —— 教科书上的经典泄漏点，很多人一看到就扑上去。
3. **Metaspace** —— 另一个经典方向，但这次它是平的。
4. **「上涨速度和流量成正比」** —— 听起来像「流量涨导致的」，
   实际上它恰恰是「按不同用户数增长」的证据。

### 最短路径（4 问）

1. **涨的是堆内还是堆外？**（先分家，堆外的排查路径完全不同）
2. **老年代的对象直方图，排前几的是什么？**（看到几百万个 HashMap$Node）
3. **它们的持有链是什么？**（找到那个 static CACHE）
4. **这个缓存有上限和过期吗？**（确认根因）

### 这一份要教会的

**「内存一直涨」不是一个诊断，它至少是三种完全不同的东西：**

| 是什么 | 特征 | 处理 |
| --- | --- | --- |
| **真泄漏** | 对象不再被使用但仍被引用，通常和某条代码路径的次数相关 | 断掉那条引用 |
| **无上限的缓存** | 功能完全正常，增长和「不同 key 的数量」成正比 | 加容量上限 + 过期（LRU） |
| **还没触发回收** | Full GC 之后能降回去，是配置问题不是泄漏 | 调 GC / 堆大小 |

**判据是「Full GC 之后老年代的存活对象是不是也在涨」** ——
涨就是前两种，不涨就是第三种。而前两种的分界是**持有链的性质**：
是「本该释放的东西被拿住了」，还是「本来就设计成一直拿着，只是没设上限」。

**顺序永远是：堆内还是堆外 → 直方图 → 持有链。**
跳过前两步直接猜「是不是 ThreadLocal / 是不是连接没关」，
是这类问题上最常见的浪费。
