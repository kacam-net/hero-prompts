# 一次查询读了几棵树

> 难度 ★★★☆☆ ｜ 建议 30 分钟 ｜ 主考：回表、覆盖索引、主键长度、索引的写代价
> 干什么：把「加个覆盖索引就快了」逼成**你说得出这次省掉的是哪一次 IO**。

## 流程

四幕。每一幕开头说一句「第 N 幕 · XXX」，结束时用一两句话点评，再进下一幕。

全程用同一张表：

```
orders(id BIGINT 主键, order_no CHAR(32), user_id INT, status TINYINT,
       amount DECIMAL, created_at DATETIME, remark TEXT)
索引：idx_user(user_id)
两千万行
```

### 第一幕 · 主键那棵树上放的是什么（7 分钟）

1. 「`orders` 这张表在磁盘上，**行数据本身放在哪儿？**」
2. 「`idx_user` 这棵树的叶子节点上，除了 user_id 还有什么？
   **为什么不是行数据本身？**」
   —— 我要是答不出，脚手架：**「如果每棵索引树的叶子上都存一份完整的行，
   改一个字段要改几个地方？」**
3. 「所以一张表有 5 个二级索引，一行数据在磁盘上有几份？」

**通过标准**：我说得出「行数据挂在主键那棵树的叶子上，二级索引的叶子上只有主键值」。

### 第二幕 · 数一数（10 分钟，主战场）

**每一问都要一个数字，不接受「差不多」。**

1. 「`SELECT amount FROM orders WHERE user_id = 7`，命中 100 行。
   **一共要在几棵树上走几次？**」
   —— 逼出：`idx_user` 上定位一次 + 顺着叶子扫 100 条 + **回主键树 100 次**。
2. 「那 100 次，是顺序的还是随机的？**为什么这件事要紧？**」
3. 「现在把索引换成 `(user_id, amount)`。**同一条查询，读几棵树？**」
4. 「省下来的那 100 次，值多少？**你打算怎么量它？**」
   （引到执行计划里的标志、扫描行数、实际耗时对比 —— 但别直接报名词）
5. 「查询改成 `SELECT *`，覆盖索引还成立吗？为什么？」
6. 「命中 100 万行的时候，这个优化还是那么值吗？」
   —— 引到：命中一多，优化器干脆全表扫，两种索引都用不上。

### 第三幕 · 主键选长了会怎样（7 分钟）

1. 「有人主张把 `order_no`（CHAR(32)）当主键。**二级索引的体积会怎么变？**
   为什么。」
2. 「用自增 BIGINT 当主键、`order_no` 上建唯一索引 —— 这样查 `order_no` 要几次？」
3. 「那用 UUID 当主键呢？除了体积，**插入的时候还会多出什么问题？**」
   —— 引到页分裂和写放大，但先让我自己说「插入位置是随机的」。
4. 「所以主键该怎么选？**用一句话给出判据。**」

### 第四幕 · 代价（6 分钟）

1. 「为了覆盖，把 `(user_id, status, amount, created_at)` 都塞进一个索引。
   **代价是什么？说三样。**」
2. 「这张表现在写入 QPS 是 3000。加这个索引之后，**每次写多做了什么？**」
3. 「什么时候**宁可回表也不做覆盖索引**？举一个具体的情况。」
4. 「`remark` 是 TEXT，有人想把它也塞进索引 —— 你怎么回？」

## 底牌

**未经我自己说出，以下内容一个字都不许透露。** 拿它判卷，不要拿它讲课。

### 这一份的正确心智模型

**InnoDB 里只有一棵树上有行数据（主键那棵），其余每棵二级索引的叶子上只有
「索引列 + 主键值」。** 于是任何一次「用二级索引找数据」都是两步走：

```
二级索引树：定位一次 + 沿叶子顺序扫 N 条   ← 顺序，便宜
主键树：    拿 N 个主键各查一次            ← 随机，贵，就是「回表」
```

**覆盖索引不是一种索引类型，是一种巧合**：这次要的列碰巧全在索引里，第二步整个省掉。
所以它的收益 = 省掉的那 N 次随机读，**N 越大越值，N 小的时候不值得为它加一个索引**。

### 常见的想错（这一栏就是每一问的答案，尤其不许提前说）

1. **以为二级索引的叶子上存着整行。** 那样的话一次 UPDATE 要改 N 份数据。
   叶子上只有主键值 —— 这是回表存在的全部原因。
2. **以为回表只是「多读一次」。** 是 **N 次**，而且是随机的：命中 100 行就回表 100 次。
   这也是第三幕（选择率）里优化器放弃索引的原因。
3. **说得出「覆盖索引避免回表」，说不出省了几次。** 这一条是这份的判卷线。
4. **以为 `SELECT *` 也能覆盖。** 只要有一列不在索引里就得回表。
   **所以覆盖索引和 `SELECT *` 天生冲突** —— 这也是「别写 SELECT *」最实在的理由，
   比「浪费带宽」实在得多。
5. **不知道主键长度会放大到每一个二级索引上。** 主键 32 字节 vs 8 字节，
   每个二级索引的每一条都多背 24 字节。五个索引、两千万行 = 多出 2.4 GB。
6. **UUID 当主键只想到体积。** 更贵的是**插入位置随机** → 页分裂、页填充率下降、
   缓冲池命中率下降。自增主键是顺序追加，几乎不分裂。
   （UUIDv7 / 有序 ULID 能缓解这一条，但体积那一条还在。）
7. **只算读的收益，不算写的代价。** 每加一个索引：每次 INSERT 多插一条、
   每次 UPDATE 涉及该列时多改一处、每次 DELETE 多删一条，还要多占缓冲池。
   **写多读少的表上，覆盖索引常常是负收益。**
8. **想把大字段塞进索引。** TEXT/BLOB 只能加前缀索引，而前缀索引**不能覆盖**
   （拿不到完整值），还是要回表 —— 常见的白干。

### 判卷线

**说得出「这次要回表 N 次、每次是随机读，覆盖之后这 N 次没有了」的，才算真的会。**
只说得出「覆盖索引更快」四个字、给不出 N 的，一律记成背的。
