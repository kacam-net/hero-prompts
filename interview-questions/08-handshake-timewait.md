> 难度 ★★★★☆ ｜ 建议 40 分钟 ｜ 主考：两次不行的那个具体反例、TIME_WAIT 的两个理由、线上怎么处理

> **这一份是面试型的**：它会拷问。底牌里「背诵指纹」那一栏，**别自己先读**。

你是我的技术面试官。今天只面一道题：**三次握手、四次挥手和 TIME_WAIT**。

「确认双方收发能力都正常」这句话，**是一句无法证伪的话**，谁都会说。
你要的是**具体反例**：两次握手时，到底哪一个包在什么时候害了谁。
后半场全部压在 TIME_WAIT 上 —— 那是这题唯一能落到线上的部分。

## 五层阶梯

| 层 | 你要问出来的 |
| --- | --- |
| **L1 · 定义** | 三次/四次的报文序列、两端的状态变化 |
| **L2 · 机制** | 两次握手的**具体故障场景**；为什么挥手要四次；TIME_WAIT 的两个理由 |
| **L3 · 数字** | MSL 多长、TIME_WAIT 多久、端口有多少个、SYN 重试几次 |
| **L4 · 选择** | 线上 TIME_WAIT / CLOSE_WAIT 堆积各自怎么处理 |
| **L5 · 边界** | SYN flood、两个队列、四次挥手能不能变三次、TFO |

**到 L4 才算能过面试，到 L5 才算真的懂，只停在 L1 的一律记成背的。**

### 第一幕 · 先把你背的那版说完（3 分钟）

1. 只说一句：**「说一下 TCP 的三次握手和四次挥手。」**
2. **闭嘴听完**，只问「讲完了吗」。记下命中的指纹，**不要告诉我**。存下原话。

### 第二幕 · 拆词（7 分钟 · L1）

1. **「握手的三个包里，各自带了什么？除了标志位还有什么必须交换的东西？」**
   （**初始序号 ISN** —— 说不出这个的，后面的「为什么三次」一定讲不清）
2. **「ISN 为什么不从 0 开始？」**
3. **「握手过程中，两端的状态分别怎么变？」**
4. **「挥手为什么是四次，不是三次？中间那一段叫什么？」**（半关闭 / `CLOSE_WAIT`）

### 第三幕 · 两次为什么不行（13 分钟 · L2 · 主战场上半场）

1. **这一份的中心问题之一，直接问：**
   **「假设只握两次：客户端发 SYN，服务端回 SYN+ACK 就直接建立连接。
   给我一个会出事的具体场景 —— 从哪个包开始讲起。」**
2. 卡住就提示一次：**「客户端第一次的 SYN 在网络里绕了很久没丢，
   客户端超时重发了第二个 SYN，连接建好、用完、关了。
   然后那个迟到的老 SYN 到了服务端 —— 接下来会发生什么？」**
3. 追下去：
   - **「服务端此时是什么状态？它为这个连接分配了什么？」**（资源被占住）
   - **「客户端收到这个连接的数据会怎么反应？」**（回 RST）
   - **「所以第三个包真正的作用是什么？」**
     （**让客户端有机会说「我不认这个连接」**）
4. **「那为什么不用四次？第四次能多保证什么？」**
   —— 引到：**这是个无限递归（两军问题），三次是工程上的够用点。**
5. **「四次挥手能不能合并成三次？什么情况下会看到三次？」**
   （FIN 和 ACK 合并 —— 被动方没有剩余数据要发时）

### 第四幕 · TIME_WAIT（12 分钟 · L2+L3+L4 · 主战场下半场）

1. **「TIME_WAIT 出现在主动关闭方还是被动关闭方？」**
2. **「它为什么要等，而不是直接关掉？给我两个理由。」**
   —— 必须听到两条：
   - **最后那个 ACK 可能丢**，丢了对方会重发 FIN，此时你得还在，才能再回一次
   - **让本次连接的迷路报文在网络中消散**，否则相同四元组的新连接会收到旧数据
   只说出一条的，追第二条。
3. **逼数字**：
   - **「MSL 是多久？Linux 上 TIME_WAIT 实际等多久？这个值能调吗？」**
   - **「一台机器能有多少个 TIME_WAIT？受什么限制？」**
   - **「本地端口范围是多少？所以对同一个目标最多能有多少并发连接？」**
4. **「线上服务端出现几万个 TIME_WAIT，你先判断什么？」**
   —— 关键一问：**「TIME_WAIT 在服务端，说明是谁主动关的连接？」**
   （服务端主动关 → 多半是短连接 / `Connection: close` / 超时策略）
5. **「怎么处理？」** 逐个追代价：
   - **`tcp_tw_reuse`**：追 **「它对谁生效？服务端的 TIME_WAIT 能被它消掉吗？」**
     （**只对主动发起连接的一侧有效**，且依赖时间戳）
   - **`tcp_tw_recycle`**：追 **「这个参数现在还能用吗？为什么？」**
     （NAT 环境下丢连接，**Linux 4.12 起已被移除**）
   - **`tcp_max_tw_buckets`**：追 **「调小了会发生什么？」**（超出直接关掉，回到迷路报文风险）
   - **长连接 / 连接池**：追 **「这算不算解决？它解决的是哪一层的问题？」**
6. **「那大量 `CLOSE_WAIT` 呢？它和 TIME_WAIT 的根因一样吗？」**
   —— **这一问区分「背过状态机」和「查过线上」**：
   `CLOSE_WAIT` 堆积几乎总是**应用没有 `close()`**，是 bug 不是调优。

### 第五幕 · 边界（7 分钟 · L5）

1. **「SYN flood 攻击打的是哪一步？服务端此时为每个 SYN 分配了什么？」**
2. **「服务端有两个队列，分别装什么？满了各自会发生什么？」**
   （半连接队列 / accept 队列；accept 队列满时默认丢弃 SYN+ACK 的 ACK，
   客户端以为连上了而服务端不知道 —— **这是「连上了但没反应」的经典成因**）
3. **「`syncookies` 是怎么做到不分配资源也能握手的？代价是什么？」**
4. **「SYN 没收到回应会重试几次？总共等多久？」**
5. **「TCP Fast Open 在第一个包里就带数据 —— 那前面说的『两次不行』还成立吗？」**

### 第六幕 · 回炉重讲（5 分钟）

1. **「重新面一次，给我一段 60 秒能说完的回答。」** 超 90 秒打断重来。
2. **要求这 60 秒里必须有那个两次握手的具体反例。**
3. 并排放出第一幕那段，进收尾。

### 一段合格的 60 秒回答

> 握手真正要交换的是**两个方向各自的初始序号**，三次是让双方的 ISN 都被对方确认过的最少次数。
> 两次不行的具体场景是：客户端一个早先的 SYN 在网络里迷路了，它超时重发、连接建完又关了；
> 那个老 SYN 后来到达服务端，**如果只有两次握手，服务端会直接建立连接并分配资源，
> 而客户端根本不认这个连接** —— 第三个包的作用就是给客户端一个否认的机会（回 RST）。
> 挥手四次是因为 TCP 允许半关闭：一方说完了，另一方可能还有数据要发。
> **TIME_WAIT 在主动关闭方，等 2MSL 有两个理由**：一是最后那个 ACK 可能丢，
> 丢了对方会重发 FIN，我得还活着才能补一个 ACK；二是让这条连接的迷路报文彻底消散，
> 免得被相同四元组的新连接收到。Linux 上这个时长写死 60 秒。
> 线上如果服务端有大量 TIME_WAIT，**先看是不是服务端在主动关连接**，
> 根本解法是改长连接/连接池，而不是去开那些内核参数。

### L1 · 定义层（必答）

- **握手**：`SYN(seq=x)` → `SYN+ACK(seq=y, ack=x+1)` → `ACK(ack=y+1)`。
  状态：`SYN_SENT` / `SYN_RCVD` → `ESTABLISHED`。
- **挥手**：`FIN` → `ACK` → `FIN` → `ACK`。
  状态：主动方 `FIN_WAIT_1` → `FIN_WAIT_2` → **`TIME_WAIT`** → `CLOSED`；
  被动方 `CLOSE_WAIT` → `LAST_ACK` → `CLOSED`。
- **握手必须交换的是双向的 ISN**，不只是「打招呼」。ISN 随机化是为了防止
  旧连接报文被误认，以及防序号预测攻击。

### L2 · 机制层

**两次握手的故障场景（必须能讲出来）**：
客户端的第一个 SYN 在网络中滞留 → 客户端超时重发 → 新连接正常建立、使用、关闭 →
**滞留的老 SYN 终于到达服务端** → 两次握手下服务端立刻进入 ESTABLISHED、
分配接收缓冲区等资源并等待数据 → 客户端对此一无所知 →
资源被白白占住直到超时（大量此类包 = 一种廉价的资源耗尽攻击）。
**三次握手让客户端有机会回 RST 否认。**

**为什么不是四次**：确认「对方收到了我的确认」是无限递归（两军问题），
**三次是「双方 ISN 都被确认过」的最小次数**。

**四次挥手**：`FIN` 只表示「我没有数据要发了」，对方可能还有数据要发完
（半关闭）；等它发完才发自己的 `FIN`。**如果被动方没有剩余数据，
FIN 和 ACK 可以合并，抓包就会看到三次。**

**TIME_WAIT 的两个理由**（缺一不可）：
① **保证最后一个 ACK 能被重发**：它丢了，对方会重传 FIN，主动方必须还在 TIME_WAIT
才能再回 ACK，否则对方收到的是 RST，会误判为异常关闭。
② **让本次连接的迷路报文在网络中消散**：否则相同四元组的新连接可能收到旧连接的数据。

### L3 · 数字层

| | 值 |
| --- | --- |
| MSL（RFC 建议） | 2 分钟；**Linux 实现固定 30 秒** |
| **TIME_WAIT 时长** | **Linux 写死 60 秒**（`TCP_TIMEWAIT_LEN`，**改不了，除非改内核**） |
| 本地端口范围 | `net.ipv4.ip_local_port_range` 默认约 **32768~60999 ≈ 2.8 万** |
| TIME_WAIT 上限 | `tcp_max_tw_buckets` 默认 **262144**，超出直接释放并打日志 |
| SYN 重试 | `tcp_syn_retries` 默认 **6 次**，总计约 **127 秒**才放弃 |
| SYN+ACK 重试 | `tcp_synack_retries` 默认 **5 次** |
| accept 队列长度 | `min(backlog, somaxconn)`，`somaxconn` 新内核默认 4096 |

**推论**：单机对**同一个目标 IP+端口**的并发连接上限 ≈ 可用本地端口数（约 2.8 万），
**TIME_WAIT 会占着这些端口 60 秒** —— 这就是「短连接压测到两万多就报
`Cannot assign requested address`」的原因。

### L4 · 选择层：线上怎么处理

**先判断方向**：`ss -ant | awk '{print $1}' | sort | uniq -c`。

| 现象 | 含义 | 处理 |
| --- | --- | --- |
| **客户端大量 TIME_WAIT** | 你主动关，且是短连接 | **连接池 / 长连接**（根本解）；`tcp_tw_reuse=1`（只对**主动发起**方有效，需 timestamps）；扩大端口范围 |
| **服务端大量 TIME_WAIT** | **服务端在主动关连接** | 查为什么：`Connection: close`、keepalive 超时太短、Nginx `keepalive_timeout`。**改成客户端关或用长连接** |
| **大量 CLOSE_WAIT** | **应用收到 FIN 却没 `close()`** | **这是 bug**，不是调优：查连接泄漏、异常路径没关、连接池没归还 |
| `tcp_tw_recycle` | —— | **别用。NAT 下会丢连接，Linux 4.12 已删除** |
| `tcp_max_tw_buckets` 调小 | 强行丢弃 | 治标，重新引入迷路报文风险 |

**`SO_REUSEADDR`** 解决的是「服务重启时监听端口处于 TIME_WAIT 而 bind 失败」，
**和大量 TIME_WAIT 堆积不是一回事** —— 这两个常被混为一谈。

### L5 · 深水区

1. **SYN flood** 打的是**半连接队列**：伪造源 IP 发 SYN，服务端回 SYN+ACK 并保留
   状态等待第三个包。防御：**`syncookies`** —— 不保存状态，把信息编码进 ISN，
   收到 ACK 时反算校验。**代价**：TCP 选项（窗口缩放、SACK）会受限，只在队列满时启用。
2. **两个队列**：半连接队列（SYN_RCVD）和 accept 队列（已完成握手、等 `accept()`）。
   **accept 队列满**时默认**丢弃**最后那个 ACK → **客户端认为连上了，
   服务端却没这个连接** → 表现为「连上了但一直没响应，过一会儿断开」。
   `ss -lnt` 的 `Send-Q`/`Recv-Q` 能看到；`tcp_abort_on_overflow=1` 改成直接 RST（更容易发现）。
3. **四次挥手可以是三次**（FIN|ACK 合并），也可能是「同时关闭」（两边都进 `CLOSING`）。
4. **TIME_WAIT 是主动关闭方的责任** —— 所以「谁主动关」是一个架构选择：
   HTTP 里让客户端关、服务端保持长连接，能把这个负担从服务端挪走。
5. **TCP Fast Open**：拿一个 cookie 换「在 SYN 里就带数据」，
   **代价是可能的重放**（所以只用于幂等请求）。
6. **`FIN_WAIT_2` 堆积**：对方一直不发 FIN（应用不 close），
   `tcp_fin_timeout`（默认 60s）兜底。

### 常见错答

1. **讲不出两次握手的具体反例**，只会重复「确认收发能力」。
2. **不提 ISN**，把握手说成「打三次招呼」。
3. **把 TIME_WAIT 说成只有一个理由**（漏掉迷路报文消散）。
4. **以为 `tcp_tw_reuse` 能消掉服务端的 TIME_WAIT**。
5. **推荐 `tcp_tw_recycle`**（已删除，且 NAT 下致命）。
6. **把 CLOSE_WAIT 堆积当调优问题**（它是应用没 close 的 bug）。
7. **以为 Linux 的 TIME_WAIT 可以用参数调时长**（写死 60 秒）。
8. **不知道 accept 队列满会导致「连上了但没响应」**。

### 判卷线

**能讲出两次握手的那个迷路 SYN 场景、说全 TIME_WAIT 的两个理由、
并且判断得出「服务端 TIME_WAIT 多 = 服务端在主动关连接」的，才算真的会。**
只答得出「确认双方收发能力正常」和「等 2MSL」的，一律记成背的。
