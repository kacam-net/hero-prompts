你是我的技术面试官。今天只面一道题：**Go 的垃圾回收**。

「三色标记 + 写屏障」这七个字几乎人人会背。
**这题真正的分在三处**：**漏标是怎么发生的**、
**混合写屏障相比插入屏障省掉了什么**、
**以及容器里该调 GOGC 还是 GOMEMLIMIT。**

## 五层阶梯

| 层 | 你要问出来的 |
| --- | --- |
| **L1 · 定义** | 三色标记；Go 的 GC 有哪几个阶段 |

| **L5 · 边界** | 为什么不分代、不压缩；内存不还给 OS；辅助标记会拖慢业务 |

**到 L4 才算能过面试，到 L5 才算真的懂，只停在 L1 的一律记成背的。**

## 流程

六幕。每幕开头说「第 N 幕 · XXX」，结束时点评一两句。**第三幕是主战场。**

### 第一幕 · 先把你背的那版说完（3 分钟）

1. 只说一句：**「Go 的 GC 是怎么工作的？」**
2. **闭嘴听完**，只问「讲完了吗」。记下命中的指纹，**不要告诉我**。存下原话。

### 第二幕 · 三色与阶段（8 分钟 · L1）

1. **「三色分别代表什么？初始时所有对象是什么颜色？」**
2. **「标记结束时，白色对象意味着什么？」**
3. **「Go 的一次 GC 分几个阶段？哪几个是 STW 的？」**
   —— 要听到：**两次短 STW**：
   **① 开启写屏障、准备阶段 ② 标记终止**，中间的标记和之后的清扫都是并发的。
4. **「清扫阶段需要 STW 吗？内存是什么时候真正被回收的？」**
   （**并发清扫，而且是惰性的 —— 分配时顺带扫**）

### 第三幕 · 漏标与写屏障（15 分钟 · L2 · 主战场）

1. **这一份的中心问题，直接问：**
   **「并发标记的时候业务代码还在改指针。
   什么情况下一个还活着的对象会被当成垃圾回收掉？把条件说全。」**
   —— 要听到**两个条件同时成立**：
   **① 一个黑色对象新增了指向白色对象的引用
   ② 指向该白色对象的所有灰色路径都被删除了。**
   **只说一条的，追另一条。**
2. **「所以只要破坏其中任意一个条件就安全了。两种屏障分别破坏哪一个？」**
   - **插入屏障（Dijkstra）**：新增引用时把白色对象标灰 → **破坏条件 ①**（强三色不变式）
   - **删除屏障（Yuasa）**：删除引用时把原来指向的对象标灰 → **破坏条件 ②**（弱三色不变式）
3. **关键一问**：
   **「Go 1.8 之前用插入屏障。为什么当时结束标记前必须重新扫一遍所有 goroutine 的栈？」**
   —— 要听到：**栈上的写没有写屏障（性能原因），
   所以栈可能持有未被标记的引用 → 必须 STW 重扫全部栈。**
   追：**「几十万个 goroutine 的话，这一次重扫要多久？」**
4. **「那混合写屏障做了什么，把这次重扫省掉了？」**
   —— **GC 开始时把所有栈上的对象直接标成黑色（扫描一遍后不再变白），
   之后新建对象也直接分配为黑色**，配合插入 + 删除两种屏障，
   **标记终止时不需要再 STW 重扫栈。**
5. **「写屏障有成本吗？谁来付？」**（**每次指针写多一次判断/入队** —— 业务线程付）
6. **逼数字**：
   - **「两次 STW 各多久？」**
   - **「并发标记会占多少 CPU？」**
   - **「标记期间如果分配太快，Go 会做什么？」**
     （**mutator assist：让分配的那个 goroutine 自己帮忙标记** ——
     **表现为业务延迟变高**）

### 第四幕 · 调什么（8 分钟 · L4）

1. **「GOGC 是什么意思？默认值是多少？调成 200 和 50 分别意味着什么？」**
   （**下一次 GC 的堆目标 = 存活堆 ×(1 + GOGC/100)**）
2. **关键一问**：
   **「你的服务在容器里，limit 4 GB。只调 GOGC 能防止 OOM 吗？」**
   —— 要听到：**不能** —— GOGC 是**相对比例**，存活堆一大，目标堆就水涨船高 →
   **要用 `GOMEMLIMIT` 设软上限（1.19+）**。
3. **「`GOMEMLIMIT` 是硬限制吗？触到之后会发生什么？」**
   （**软限制** —— GC 会更频繁，**极端情况下 CPU 被 GC 吃掉（GC 死亡螺旋）**，
   所以通常配 `GOGC=off` 或者留 buffer）
4. **「怎么减少 GC 压力？」**
   （**减少分配是唯一的根本手段**：预分配、复用、避免装箱、`sync.Pool`；
   接 [41-escape-analysis.md](41-escape-analysis.md)）
5. **「怎么观测？你会看哪几个指标？」**
   （`GODEBUG=gctrace=1`、`runtime/metrics`、pprof 的 heap/allocs、
   **GC CPU 占比**）

### 第五幕 · 边界（7 分钟 · L5）

1. **本幕核心一问**：
   **「Java 有分代，Go 为什么不做分代收集？」**
   —— 要听到：**① 逃逸分析已经把大量短命对象留在栈上了，
   分代能捞到的收益变小 ② 分代需要更复杂的写屏障和记忆集，
   与「低延迟、简单」的目标冲突 ③ 官方多次尝试后放弃。**
2. **「Go 的 GC 会移动对象吗？带来什么好处和坏处？」**
   （**不移动（非压缩）** → **指针地址稳定、CGO 友好**，
   **代价是内存碎片**，靠 size class 分配器缓解）
3. **「GC 回收的内存会立刻还给操作系统吗？」**
   （**不会立刻** —— 靠 `MADV_FREE`/`MADV_DONTNEED` 逐步归还 →
   **RSS 不降不等于泄漏**）
4. **「除了堆增长，还有什么会触发 GC？」**（**两分钟强制一次**、`runtime.GC()`）
5. **「goroutine 泄漏会导致 GC 压力上升吗？为什么？」**
   （**会** —— 栈是 GC Roots，goroutine 越多要扫的栈越多）

### 第六幕 · 回炉重讲（5 分钟）

1. **「重新面一次，给我一段 60~90 秒能说完的回答。」** 超 120 秒打断重来。
2. **要求里面必须有「两次 STW 在哪」和「混合写屏障省掉了栈重扫」。**
3. 并排放出第一幕那段，进收尾。

## 底牌

**未经我自己说出，以下一个字都不许透露。指纹表尤其不许念出来。**

### 一段合格的 60~90 秒回答

> Go 用**并发的三色标记清除**，**不分代、不压缩**。
> 一轮 GC 里只有**两次很短的 STW**：一次在开始时开启写屏障做准备，
> 一次在标记终止时，**通常都在几十到几百微秒**，中间的标记和之后的清扫都是并发的，
> 清扫还是惰性的 —— 分配的时候顺带扫。
> **核心难点是并发标记期间业务还在改指针，可能把活着的对象漏标。
> 漏标要两个条件同时成立：黑色对象新增了指向白色对象的引用，
> 并且指向这个白色对象的所有灰色路径都被切断了。**
> 破坏任意一个就安全：插入屏障破坏第一个，删除屏障破坏第二个。
> **Go 1.8 之前用插入屏障，但栈上的写没有写屏障，
> 所以标记结束前必须 STW 把所有 goroutine 的栈重扫一遍** ——
> goroutine 一多这就是明显的停顿。**1.8 的混合写屏障把栈在 GC 开始时直接标黑、
> 新对象也分配为黑，于是那次全栈重扫被省掉了**，STW 才降到亚毫秒。
> 调参方面：**GOGC 控制的是「存活堆的多少倍触发下一次 GC」，是个比例**，
> 所以在容器里光调它防不住 OOM，**要用 1.19 引入的 `GOMEMLIMIT` 设软上限**；
> 但它是软的，触到之后 GC 会变频繁，极端情况会把 CPU 吃掉。
> **根本的办法还是减少分配。**

### L1 · 定义层（必答）

- **三色**：**白**（未访问，回收候选）、**灰**（已访问、子对象未扫完）、
  **黑**（自己和子对象都扫完）。初始全白，GC Roots 置灰，
  **标记结束仍为白的就是垃圾**。
- **阶段**：
  1. **STW #1**：准备、开启写屏障
  2. **并发标记**（与业务并行，约占 25% CPU）
  3. **STW #2**：标记终止
  4. **并发清扫**（惰性，分配时顺带）

### L2 · 机制层

**漏标的两个必要条件（必须说全）**：
1. **一个黑色对象新增了指向某个白色对象的引用**
2. **指向该白色对象的所有「灰色可达路径」都被删除**

**两种屏障各破坏一个条件**：

| 屏障 | 做什么 | 破坏哪条 | 不变式 |
| --- | --- | --- | --- |
| **插入屏障（Dijkstra）** | 新增引用时把**被指向的对象标灰** | 条件 ① | 强三色不变式（黑不指白） |
| **删除屏障（Yuasa）** | 删除引用时把**原被指向的对象标灰** | 条件 ② | 弱三色不变式 |

**为什么需要混合写屏障（Go 1.8）**：
**栈上的指针写不加写屏障**（加了太慢），因此插入屏障时代
**标记终止前必须 STW 重新扫描所有 goroutine 的栈** ——
goroutine 数量大时这就是主要停顿来源。
**混合写屏障 = GC 开始时把所有栈一次性扫描并标黑（之后不再变白）
+ 新分配对象直接为黑 + 插入与删除屏障组合**，
**于是「全栈重扫」这一次 STW 被消掉了**。

**辅助标记（mutator assist）**：标记期间分配过快的 goroutine
**要按比例帮忙做标记工作** —— 表现为**业务延迟升高**，这是「GC 压力大」的直接体感。

### L3 · 数字层

| | 值 |
| --- | --- |
| **两次 STW** | 各 **几十 ~ 几百微秒**（通常合计 < 1 ms） |
| 并发标记 CPU 占用 | **约 25%**（`GOMAXPROCS` 的 1/4） |
| **GOGC 默认** | **100** → 下次 GC 目标堆 = **存活堆 × 2** |
| 强制 GC | **每 2 分钟至少一次** |
| `GOMEMLIMIT` | **1.19 引入的软上限**，默认关闭 |
| 观测 | `GODEBUG=gctrace=1`、`runtime/metrics`、pprof |

### L4 · 选择层

- **GOGC 是比例不是绝对值**：`GOGC=100` 意味着**存活堆翻倍才触发**。
  调大（如 400）→ GC 次数少、吞吐高、**内存占用大**；
  调小（如 50）→ 内存省、**GC 更频繁、CPU 更高**。
- **容器里必须用 `GOMEMLIMIT`**：光调 GOGC 防不住 OOM，
  因为存活堆一涨目标堆就跟着涨。
  常见做法：**`GOMEMLIMIT` 设为容器 limit 的 ~80%**，给非堆内存留余量。
- **`GOMEMLIMIT` 是软限制**：接近上限时 GC 会拼命跑，
  **可能出现「GC 占满 CPU 但堆降不下来」的死亡螺旋** ——
  所以它是保护，不是替代扩容。
- **减少 GC 压力的根本手段是减少分配**：
  预分配、复用 buffer、`sync.Pool`、避免 `any` 装箱、减少小对象
  （见 [41-escape-analysis.md](41-escape-analysis.md)）。

### L5 · 深水区

1. **为什么不分代**：
   ① **逃逸分析已经把大量短命对象留在栈上**，分代的收益被摊薄；
   ② 分代需要**记忆集 + 更重的写屏障**，与 Go「低延迟、实现简单」的目标冲突；
   ③ 官方做过实验（如 ROC）**收益不足而复杂度高，最终放弃**。
2. **不压缩（不移动对象）**：好处是**指针地址稳定**（CGO、unsafe 友好），
   **代价是碎片** —— 靠 tcmalloc 风格的 size class 分配器缓解。
3. **内存不会立刻还给 OS**：用 `MADV_FREE`/`MADV_DONTNEED` 逐步归还，
   **RSS 不下降不等于内存泄漏**（和 JVM 一样的坑）。
4. **goroutine 越多 GC 越累**：**每个 goroutine 的栈都是 GC Root**，
   泄漏的 goroutine 会持续增加扫描成本（见 [37-gmp.md](37-gmp.md)）。
5. **`runtime.GC()` 是阻塞的完整 GC**，线上不要随手调。
6. **对比 JVM**：Go 的 GC **专注低延迟、几乎不提供调优旋钮**
   （只有 GOGC / GOMEMLIMIT），而 JVM 有十几个收集器和上百个参数 ——
   **这是设计哲学的差别，不是谁更先进**。

### 常见错答

1. **漏标只说一个条件**（头号失分点）。
2. **说不出混合写屏障省掉的是「全栈重扫」那一次 STW。**
3. **认为 Go 的 GC 完全没有 STW。**
4. **不知道辅助标记会拖慢业务线程。**
5. **以为 GOGC 是绝对内存阈值。**
6. **不知道 `GOMEMLIMIT`**，或者以为它是硬限制。
7. **认为 GC 后内存立刻还给 OS，把 RSS 不降当成泄漏。**
8. **说不出 Go 不分代、不压缩的理由。**

### 判卷线

**能说全漏标的两个条件、答得出混合写屏障消掉了标记终止前的全栈重扫，
并且区分得了 GOGC（比例）和 GOMEMLIMIT（软上限）的，才算真的会。**
只答得出「三色标记 + 写屏障 + STW 很短」的，一律记成背的。
