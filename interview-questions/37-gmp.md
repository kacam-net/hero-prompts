# GMP 调度模型

> 难度 ★★★★☆ ｜ 建议 40 分钟 ｜ 主考：P 为什么存在、陷入系统调用时怎么解绑、抢占是怎么做到的
> 干什么：把「G 是协程、M 是线程、P 是处理器」逼成
> **「P 是可运行队列的持有者 —— 所以 M 陷入系统调用时，把 P 交出去比什么都重要」**。
> 用法：把下面分隔线之后的全部内容复制给一个**新对话**的大模型，然后等它问第一个问题。
>
> **这一份是面试型的**：它会拷问。底牌里「背诵指纹」那一栏，**别自己先读**。
>
> 按 **Go 1.14+** 讲。相关：
> [../computer-systems/06-context-switch.md](../computer-systems/06-context-switch.md)。

你是我的技术面试官。今天只面一道题：**Go 的 GMP 调度模型**。

三个字母的含义谁都背得出。**真正分人的是三问**：
**「为什么需要 P，没有它会怎样？」**、
**「一个 goroutine 陷入阻塞的系统调用，另外几万个还跑得动吗？」**、
**「一个死循环的 goroutine 能被抢占吗？」**

## 五层阶梯

| 层 | 你要问出来的 |
| --- | --- |
| **L1 · 定义** | G / M / P 各是什么、数量各由什么决定 |
| **L2 · 机制** | 本地队列与全局队列、work stealing、系统调用时的解绑、抢占 |
| **L3 · 数字** | 初始栈多大、创建多快、队列多长、抢占阈值 |
| **L4 · 选择** | GOMAXPROCS 怎么设；容器里的坑；要不要 worker pool |
| **L5 · 边界** | goroutine 泄漏、网络 IO 不占 M、CGO 会占 M |

**到 L4 才算能过面试，到 L5 才算真的懂，只停在 L1 的一律记成背的。**

## 流程

六幕。每幕开头说「第 N 幕 · XXX」，结束时点评一两句。**第三幕是主战场。**

### 第一幕 · 先把你背的那版说完（3 分钟）

1. 只说一句：**「讲一下 Go 的 GMP 调度模型。」**
2. **闭嘴听完**，只问「讲完了吗」。记下命中的指纹，**不要告诉我**。存下原话。

### 第二幕 · P 为什么存在（8 分钟 · L1+L2）

1. **「G、M 的数量各由什么决定？P 呢？」**
2. **这一幕的关键一问**：
   **「如果只有 G 和 M，用一个全局队列让所有线程去抢 —— 会有什么问题？」**
   —— 要听到：**全局锁竞争、没有局部性**。
3. **「所以 P 手里具体握着什么？」**（**本地可运行队列 + 内存分配缓存（mcache）**）
4. **「一个 M 想跑 G，必须先拿到什么？」**（**必须绑定一个 P**）
5. **「本地队列空了怎么办？」**（**从全局队列取 / 从别的 P 偷一半 / 查 netpoller**）

### 第三幕 · 阻塞与抢占（15 分钟 · L2+L3 · 主战场）

1. **这一份的中心问题，直接问：**
   **「一个 goroutine 调了一个阻塞的系统调用，比如读本地文件。
   这个 M 被卡住了 —— 那它手上那个 P 的本地队列里排着的几百个 G 怎么办？」**
   —— 要听到：**P 会和 M 解绑（handoff），交给另一个 M（或新建 M）继续跑。**
   追：**「谁来发现这件事？」**（**sysmon**）
2. **「那如果是网络 IO 呢？也会解绑吗？」**
   —— 关键区别：**网络 IO 走 netpoller（epoll），G 被挂起但 M 不阻塞** ——
   **这是 Go 能用少量线程扛住海量连接的根本原因。**
3. **「CGO 调用呢？」**（**会占住 M**，和阻塞系统调用类似）
4. **第二个关键问题**：
   **「一个 goroutine 里写了 `for {}`，什么都不调用。
   调度器能把它换下来吗？」**
   —— 要分版本讲：**1.14 之前不能（协作式抢占靠函数调用时的栈检查）,
   会导致该 P 被独占、甚至 GC 都停不下来；1.14 之后用信号做异步抢占。**
   追：**「用的什么信号？抢占的时机在哪？」**（`SIGURG`）
5. **「sysmon 还干了哪些事？」**（**抢占跑太久的 G、回收长时间 syscall 的 P、
   强制触发 GC、归还内存**）
6. **逼数字**：
   - **「goroutine 初始栈多大？能长到多大？」**
   - **「创建一个 goroutine 多少纳秒？和创建线程差多少？」**
   - **「P 的本地队列能放多少个 G？满了怎么办？」**
   - **「sysmon 认为『跑太久』的阈值是多少？」**

### 第四幕 · 逼选型（7 分钟 · L4）

1. **「`GOMAXPROCS` 你会设成多少？」**
2. **关键坑**：**「你的服务跑在容器里，limit 是 2 核。
   Go 程序读到的 `GOMAXPROCS` 是多少？」**
   —— **默认读的是宿主机的核数**（如 64）→ **P 太多、频繁上下文切换、
   GC 的 worker 也按它算** → 用 **`automaxprocs`** 或显式设置。
   **这一问几乎是「有没有在容器里跑过 Go」的试金石。**
3. **「Go 里还需要 worker pool 吗？既然 goroutine 这么便宜。」**
   —— 追：**「每个请求开一个 goroutine，下游只能扛 100 并发，会发生什么？」**
   （**goroutine 便宜，但它背后的资源不便宜** —— 要用信号量/池限制并发）
4. **「一台机器上几十万 goroutine，瓶颈在哪？」**（内存 + 调度 + GC 扫描栈）

### 第五幕 · 边界（7 分钟 · L5）

1. **「goroutine 泄漏最常见的形状是什么？」**
   （**向没人接收的 channel 发送 / 从没人发送的 channel 接收 / 没传 context**）
2. **「怎么发现 goroutine 泄漏？」**（`runtime.NumGoroutine()` 曲线、
   **pprof 的 goroutine profile**）
3. **「goroutine 的栈是怎么增长的？增长的那一刻发生了什么？」**
   （**morestack → 分配更大的栈 → 拷贝 → 调整指针**；
   追：**「所以栈上的指针会变吗？」**）
4. **「M 的数量有上限吗？超了会怎样？」**（默认 **10000**，超了直接 crash）
5. **「Go 的调度是抢占式还是协作式？」**
   （**混合** —— 1.14 之后有基于信号的异步抢占，但 GC 的某些点仍需协作）

### 第六幕 · 回炉重讲（5 分钟）

1. **「重新面一次，给我一段 60~90 秒能说完的回答。」** 超 120 秒打断重来。
2. **要求里面必须有「P 持有本地队列」和「系统调用时的解绑」。**
3. 并排放出第一幕那段，进收尾。

## 底牌

**未经我自己说出，以下一个字都不许透露。指纹表尤其不许念出来。**

### 一段合格的 60~90 秒回答

> G 是 goroutine，M 是操作系统线程，**P 是调度的上下文，它持有一个本地可运行队列
> 和内存分配缓存** —— **一个 M 必须先绑定一个 P 才能跑 G**。
> P 存在的意义就是把「所有线程抢一个全局队列」变成「各跑各的本地队列」，
> 减少锁竞争、提高局部性；本地队列空了就去全局队列拿，
> 或者**从别的 P 偷一半**过来。
> **最关键的机制是阻塞时的处理**：
> 如果一个 M 陷入阻塞的系统调用，**sysmon 会把它的 P 摘下来交给别的 M**，
> 这样这个 P 队列里的几百个 G 不会被一个系统调用拖住；
> 而**网络 IO 走的是 netpoller，G 挂起但 M 不阻塞**，
> 这才是 Go 能用几十个线程扛住百万连接的原因。
> 抢占方面，**1.14 之前是协作式的 —— 一个纯计算的 `for{}` 死循环抢不下来**，
> 之后引入了**基于 SIGURG 信号的异步抢占**。
> 数字上：goroutine 初始栈 **2 KB**、可增长；创建一个大概几百纳秒，
> 比创建线程便宜两个数量级；P 的本地队列是 256。
> 一个实战坑是**容器里 `GOMAXPROCS` 默认读的是宿主机核数**，
> 要用 automaxprocs 或者显式设置。

### L1 · 定义层（必答）

| | 是什么 | 数量 |
| --- | --- | --- |
| **G** | goroutine：栈 + 上下文 + 状态 | 你创建多少就有多少（十万级常见） |
| **M** | 操作系统线程 | 按需创建，**上限默认 10000** |
| **P** | **调度上下文**：持有**本地可运行队列**和 **mcache** | **= `GOMAXPROCS`**，默认核数 |

**一个 M 必须持有一个 P 才能执行 G。**

### L2 · 机制层

- **为什么要有 P**：纯 G-M 模型下所有线程抢一个**全局队列 + 全局锁** →
  竞争激烈、没有局部性、内存分配也要全局同步。
  P 把队列和 mcache 本地化。
- **找活儿的顺序**：本地队列 →（每 61 次调度查一次）全局队列 →
  **netpoller** → **从其他 P 偷一半（work stealing）**。
- **系统调用**：
  - **阻塞的系统调用**（文件 IO、CGO）→ M 被内核挂起 →
    **P 与 M 解绑（handoff）**，交给空闲 M 或新建 M 继续跑该 P 的队列。
    M 返回后若拿不到 P，就把 G 放回全局队列、自己进空闲线程池。
  - **网络 IO** → **走 netpoller（epoll/kqueue）**，
    **G 被挂起、M 继续跑别的 G**，不阻塞线程。
- **抢占**：
  - **≤1.13 协作式**：只在函数调用的栈增长检查点让出 →
    **`for {}` 这样的纯计算循环永远不让出**，会卡住该 P，甚至让 STW 无法完成。
  - **1.14+ 异步抢占**：sysmon 发现 G 运行超过阈值，**向 M 发 `SIGURG` 信号**，
    在信号处理里插入抢占。
- **sysmon**（不占 P 的后台监控线程）：抢占长时间运行的 G、
  回收陷入 syscall 太久的 P、强制 GC、归还空闲内存。

### L3 · 数字层

| | 值 |
| --- | --- |
| goroutine 初始栈 | **2 KB**，按需增长（64 位上限默认 **1 GB**） |
| 创建一个 goroutine | **几百 ns**（线程是几十 μs，**差约两个数量级**） |
| goroutine 切换 | **几十~几百 ns**（用户态，不进内核） |
| P 本地队列 | **256 个 G**，满了会把**一半移到全局队列** |
| sysmon 抢占阈值 | **10 ms** |
| M 上限 | **10000**（`SetMaxThreads`），超出直接崩溃 |
| 全局队列检查 | 每 **61** 次调度查一次（防饿死） |

### L4 · 选择层

- **`GOMAXPROCS`**：默认 = 机器核数。
  **容器里的坑**：Go 读的是 **宿主机核数**（如 64），而 cgroup limit 只有 2 核 →
  **P 过多 → 线程频繁切换、GC worker 数量也按它算 → 延迟劣化**。
  **解法**：`go.uber.org/automaxprocs` 或启动时按 limit 显式设置。
  （Go 1.25 起对 cgroup 有了感知，但线上仍应显式确认。）
- **要不要 worker pool**：**goroutine 便宜，但它持有的资源不便宜** ——
  每请求一个 goroutine 且无限制时，下游连接池、内存、DB 会先崩。
  **用带缓冲的 channel 或 `semaphore` 限并发**，比池化更符合 Go 的写法。
- **几十万 goroutine 的瓶颈**：**内存（每个至少 2 KB 起 + 业务对象）、
  GC 扫描栈的开销、调度器压力**。

### L5 · 深水区

1. **goroutine 泄漏的三种常见形状**：
   ① 向**没有接收者**的 channel 发送
   ② 从**永远不会有数据**的 channel 接收
   ③ **没有把 `context` 传下去**，上游取消了它还在跑。
   **发现方式**：`runtime.NumGoroutine()` 监控曲线 + **pprof 的 goroutine profile**。
2. **网络 IO 不占 M 是 Go 并发模型的关键**：
   `net` 包底层把 fd 设为非阻塞并注册到 netpoller，
   **所以「一个连接一个 goroutine」这种写法才可行**。
3. **CGO 调用会占住 M**（和阻塞系统调用同类），CGO 密集的服务线程数会明显上升。
4. **栈增长**：函数入口检查栈空间不足 → `morestack` → **分配两倍大的新栈 →
   整栈拷贝 → 修正栈上的指针**。所以**栈地址会变**，
   这也是 Go 里不能长期持有栈地址给 C 用的原因。
5. **抢占不是万能的**：GC 的某些阶段仍需要 G 到达安全点；
   紧密的无函数调用循环在老版本上是 STW 杀手。
6. **G 的状态**：`_Grunnable`、`_Grunning`、`_Gwaiting`、`_Gsyscall` ——
   `_Gwaiting` 的 G 不占 P。

### 常见错答

1. **说不出 P 存在的理由**（只会背「处理器」）。
2. **不区分阻塞系统调用和网络 IO 的处理方式**（头号失分点）。
3. **认为 Go 一直是完全抢占式的**，不知道 1.14 的分界。
4. **不知道容器里 `GOMAXPROCS` 的坑。**
5. **认为 goroutine 可以无限开。**
6. **说不出 work stealing 偷多少、以及找活儿的顺序。**
7. **不知道栈增长会整栈拷贝、地址会变。**
8. **不知道 CGO 会占用 M。**

### 判卷线

**说得出「P 持有本地队列，M 必须绑 P 才能跑 G」、
「阻塞系统调用时 P 会被交出去，而网络 IO 走 netpoller 不占 M」，
并且知道 1.14 异步抢占的，才算真的会。**
只背得出三个字母含义的，一律记成背的。
