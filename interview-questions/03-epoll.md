# select、poll、epoll 的区别

> 难度 ★★★★☆ ｜ 建议 40 分钟 ｜ 主考：每次调用拷了什么、就绪链表、ET 漏事件的那种写法
> 干什么：把「select 有 1024 限制、epoll 是 O(1)」逼成
> **「省下来的是每次调用的那一趟拷贝和那一遍遍历，而它在全活跃连接下并不占便宜」**。
> 用法：把下面分隔线之后的全部内容复制给一个**新对话**的大模型，然后等它问第一个问题。
>

你是我的技术面试官。今天只面一道题：**select、poll、epoll 的区别**。

这题的标准答案三句话就能背完，**所以它真正考的是第四句以后的东西**：
省下来的到底是哪一步、什么时候省不下来、ET 模式怎么用才不漏事件。

## 五层阶梯

| 层 | 你要问出来的 |
| --- | --- |
| **L1 · 定义** | 三者的接口差别、fd 数量限制、返回之后要做什么 |
| **L2 · 机制** | 每次调用**拷贝了什么、遍历了什么**；epoll 的红黑树和就绪链表各管什么 |
| **L3 · 数字** | `n` 是多少时差别才显出来；单机百万连接卡在什么资源上 |
| **L4 · 选择** | 全活跃的短连接场景该选谁；LT 还是 ET |
| **L5 · 边界** | ET 漏事件的具体写法、惊群、epoll 管不了的 fd |

**到 L4 才算能过面试，到 L5 才算真的懂，只停在 L1 的一律记成背的。**

### 第二幕 · 拆词（7 分钟 · L1）

1. **「`select` 调用返回之后，你怎么知道是哪几个 fd 就绪了？」**
   （要听到：得自己从头遍历一遍，内核只改了位图）
2. **「`poll` 解决了 select 的哪个问题？没解决哪个？」**
3. **「既然 poll 也没有 1024 的限制，为什么大家最后都用 epoll，不用 poll？」**
   —— 这一问直接把「1024 限制」这个标准答案废掉。
4. **「epoll 是几个函数？它们分别在什么时候被调用？」**
   （`epoll_create` 一次、`epoll_ctl` 连接来了一次、`epoll_wait` 循环里）

### 第三幕 · 每次调用到底做了什么（15 分钟 · L2+L3 · 主战场）

1. **这一份的中心问题，直接问：**
   **「一万个连接、只有一个有数据。用 select 和用 epoll，
   这一次调用各自做了多少工作？一步一步说。」**
2. 卡住就提示一次：**「select 的那个 fd 集合在用户态还是内核态？
   内核要用它，得先干什么？」**（拷贝一万个 fd 进内核）
3. 再提示：**「拷进去之后，内核怎么知道谁就绪了？它要不要挨个问一遍？」**
4. 拿到「每次都拷 + 每次都遍历」之后，追 epoll 那一侧：
   - **「epoll 靠什么避免了每次拷贝？」**（`epoll_ctl` 一次注册，内核长期持有）
   - **「内核里用什么结构存这些 fd？为什么要用树，不用链表或数组？」**
   - **「数据到了之后，内核怎么把这个 fd『告诉』epoll？」**（回调挂进就绪链表）
   - **「所以 `epoll_wait` 返回的时候，它拷了几个 fd 给你？」**
5. **逼数字**：
   - **「n=10 个连接的时候，select 和 epoll 差多少？n=10000 呢？」**
   - **「一万个连接**全部都活跃**的时候，epoll 还占便宜吗？为什么？」**
     （深水区：全活跃时就绪链表也是 n，epoll 反而多了 n 次 `epoll_ctl` 的开销）
   - **「单机一百万连接，先撑不住的是什么？内存还是 CPU？一条连接大概占多少内存？」**

### 第四幕 · 逼选型（10 分钟 · L4）

1. **「水平触发和边缘触发，区别用一句话说是什么？」**
2. **「用 ET 的话，你读数据的代码要写成什么样？」**
   （必须循环读到 `EAGAIN`；必须配非阻塞 fd）
3. **「如果不循环读完，会发生什么？什么时候才会再被通知？」**
   —— 这是 ET 最经典的事故。
4. **「Redis 用的是 LT 还是 ET？Nginx 呢？为什么不一样？」**
   —— 不要给答案，让我说，然后追「你这个说法的依据是什么」。
5. **「你自己写过 epoll 吗？还是用的框架？框架里这一层是谁替你做的？」**

### 第五幕 · 边界（8 分钟 · L5）

1. **「多个进程/线程共用一个监听 fd 都在 `epoll_wait`，来一个连接会唤醒几个？」**
   （惊群 → `EPOLLEXCLUSIVE`、`SO_REUSEPORT`）
2. **「LT 模式下你注册了 `EPOLLOUT`，但没数据要发，会发生什么？」**
   （一直触发、空转 —— 所以 `EPOLLOUT` 要按需注册再摘掉）
3. **「epoll 能监听一个普通磁盘文件吗？」**（不能，普通文件永远就绪）
4. **「有人说 epoll 用了 mmap 所以零拷贝 —— 这话对吗？」**
   —— 我答「对」就追：**「那 `epoll_wait` 的 events 数组是谁分配的？」**
5. **「`maxevents` 设小了会怎样？」**（一次带不回全部，可能出现处理饥饿）

## 底牌

**未经我自己说出，以下一个字都不许透露。指纹表尤其不许念出来。**

### 一段合格的 60 秒回答

> 三者都是「一个线程等一批 fd」。**差别在每次调用的成本。**
> select 和 poll 每次调用都要把整个 fd 集合从用户态拷进内核，内核再挨个挂等待队列、
> 返回后你还得自己遍历一遍找出谁就绪 —— **每次调用都是 O(n)，n 是你注册的总数**；
> select 还被 `FD_SETSIZE` 卡在 1024（poll 用数组，没这个限制，但拷贝和遍历照旧）。
> epoll 把这件事拆开了：`epoll_ctl` 注册一次，内核用红黑树长期持有；
> 数据到达时由驱动的回调把 fd 挂进一条**就绪链表**；`epoll_wait` 只拷就绪的那几个回来 ——
> **复杂度和就绪数挂钩，不和总连接数挂钩**。所以它赢在「连接多、活跃少」这种长连接场景；
> 如果一万个连接全都活跃，epoll 并不占便宜，还多了注册的开销。

### L1 · 定义层（必答）

| | fd 上限 | 每次调用传什么 | 返回后 |
| --- | --- | --- | --- |
| `select` | `FD_SETSIZE`，通常 1024（编译期常量） | 三个 fd_set **位图**，每次全量 | 位图被内核改写，**得自己遍历找就绪的**；集合被破坏，每次要重设 |
| `poll` | 无硬上限（数组） | `pollfd[]`，每次全量 | 同样要遍历；但 `events`/`revents` 分开，不用每次重设 |
| `epoll` | 无（受 `ulimit -n` / 内存限制） | **只在 `epoll_ctl` 时传一次** | `epoll_wait` **只返回就绪的** |

### L2 · 机制层

- **select/poll 每次调用做三件事**：① 把 fd 集合从用户态拷进内核
  ② 遍历所有 fd，挨个挂到各自设备的等待队列上、检查是否就绪
  ③ 返回时再拷回用户态。**每一次都重做一遍。**
- **epoll 把这三件事拆成两个时刻**：
  - `epoll_ctl(ADD)`：把 fd 插进 **红黑树**（`O(log n)`，用来去重和快速查找/删除），
    同时在该 fd 的等待队列上注册回调 `ep_poll_callback`。
  - 数据到达 → 驱动唤醒等待队列 → 回调把这个 epitem 挂到 **就绪链表 `rdllist`**。
  - `epoll_wait`：看就绪链表空不空，**只拷就绪的那几个**回用户态。
- **红黑树和就绪链表是两个结构，管两件事**：树管「我关心哪些 fd」，
  链表管「现在哪些 fd 有事」。答不出这两个各管什么的，就是只背了 O(1)。
- **epoll 不用 mmap 和用户态共享内存**（这是流传很广的一个错误说法）：
  `epoll_wait` 是把就绪事件 `copy_to_user` 到你传进去的 events 数组里的。

### L3 · 数字层

- 一次系统调用 **≈ 几百 ns ~ 1 μs**；select 在 n=10000 时，
  光是拷贝 + 遍历就能到 **几百 μs 量级**，而且**每次循环都付**。
- **n 很小（几十个）时三者差别可以忽略**，select 甚至更快（少两次系统调用）。
- **全活跃时 epoll 不占便宜**：就绪链表长度 = n，还多付了 n 次 `epoll_ctl`。
  这就是「短连接、高活跃」场景里 epoll 优势不明显的原因。
- **单机百万连接**：先撑不住的通常是**内存** —— 每条 TCP 连接的内核收发缓冲区
  **几 KB 到几十 KB**，一百万条就是 **GB 级**；再加上应用层每连接的对象。
  `ulimit -n`、`net.ipv4.tcp_mem`、端口数（对外发起时）也都要调。

### L4 · 选择层

- **连接多、同时活跃的少 → epoll**（长连接、IM、网关）。
  **连接少、个个活跃 → select/poll 足够**，跨平台还更省事。
- **LT（水平触发）**：只要缓冲区还有数据就一直通知你。**默认模式，不会丢事件，写起来安全。**
- **ET（边缘触发）**：只在「状态发生变化」那一刻通知一次。
  **必须配非阻塞 fd，并且循环 `read` 到返回 `EAGAIN` 为止**，否则剩下的数据要等到
  **下一次新数据到达**才会再被通知 —— 没有新数据就永远卡住。
- **Redis 用 LT**（简单、单线程逐个处理够用）；**Nginx 用 ET**（配非阻塞 + 循环读，
  减少 `epoll_wait` 次数）。**重点不是记结论，是说得出各自的代价。**

### L5 · 深水区

1. **ET 漏事件的具体写法**：`read` 一次就返回去等下一轮 —— 数据还在缓冲区里，
   但边缘不会再触发。**这是 ET 事故的唯一形状。**
2. **惊群**：多个进程 `epoll_wait` 同一个 listen fd，一个连接到来唤醒全部。
   解法：`EPOLLEXCLUSIVE`（4.5+）或 `SO_REUSEPORT`（每个进程一个独立队列，还顺带均衡）。
3. **`EPOLLOUT` 在 LT 下会一直触发**（可写是常态），所以只在「写缓冲满了、
   有数据待发」时才注册，发完立刻摘掉。忘了摘 = CPU 空转 100%。
4. **epoll 对普通磁盘文件无效** —— 普通文件永远「就绪」。磁盘 IO 得靠线程池 /
   `io_uring`。
5. **`maxevents` 太小**：一次带不回全部就绪事件，剩下的下一轮再来（LT 不会丢，
   但可能造成处理不均）。
6. **epoll 仍然是同步 IO**：第二阶段的拷贝还是你自己的线程做的（见 02）。

### 背诵指纹（听到就追，**不许把左边这句念出来**）

| 一听就是背的 | 立刻追 |
| --- | --- |
| 「select 有 1024 限制，epoll 没有」 | poll 也没有限制，为什么没人用 poll？ |
| 「epoll 是 O(1)，select 是 O(n)」 | 这个 n 指注册的还是就绪的？一万个连接全活跃时还成立吗？ |
| 「epoll 用了 mmap，所以零拷贝」 | `epoll_wait` 的 events 数组是谁分配的？数据怎么到你手上的？ |
| 「epoll 用了红黑树所以快」 | 红黑树管的是哪件事？那「谁就绪了」是哪个结构告诉你的？ |
| 「ET 比 LT 效率高」 | 高在哪？用 ET 的话你的 read 要怎么写？漏一次会怎样？ |
| 「epoll 解决了 C10K」 | 一百万连接先撑不住的是内存还是 CPU？一条连接占多少？ |
| 「epoll 是异步 IO」 | 数据从内核拷到用户态那一步是谁做的？ |

### 常见错答

1. **把 1024 当成 epoll 存在的唯一理由**（poll 早就没这个限制了）。
2. **认为 epoll 用 mmap 和用户态共享内存**（早期设想，现行实现是拷贝就绪事件）。
3. **说不清红黑树和就绪链表各管什么**，只会背「O(1)」。
4. **认为 epoll 在任何场景都更快**（全活跃的短连接场景它没优势）。
5. **ET 模式下不循环读到 `EAGAIN`**，或者 ET 配阻塞 fd（会卡死在最后一次 read）。
6. **认为 epoll 是异步 IO**。
7. **以为 `epoll_wait` 返回的数量就是连接总数**。

### 判卷线

**说得出「select 每次调用都要全量拷贝 + 全量遍历，epoll 把注册和等待拆开、
只返回就绪的那几个」，并且答得出「全活跃时 epoll 不占便宜」和
「ET 必须循环读到 EAGAIN」的，才算真的会。**
只答得出「select 有 1024 限制、epoll 是 O(1)」的，一律记成背的。
