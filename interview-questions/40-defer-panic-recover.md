你是我的技术面试官。今天只面一道题：**defer、panic 和 recover**。

这题几乎全部用代码题来问。**三个点能立刻分出层次**：
**`defer fmt.Println(i)` 里的 `i` 是什么时候求值的**、

### 第二幕 · 求值时机（7 分钟 · L1+L2）

1. ```go
   i := 0
   defer fmt.Println(i)
   i = 10
   // 输出什么？
   ```
   —— **0**。追：**「为什么不是 10？」**（**参数在注册时就求值了**）
2. ```go
   i := 0
   defer func() { fmt.Println(i) }()
   i = 10
   // 输出什么？
   ```
   —— **10**。追：**「这两段差在哪一个字上？」**（闭包捕获的是变量本身）
3. ```go
   for i := 0; i < 3; i++ { defer fmt.Println(i) }
   // 输出顺序？
   ```
   （2 1 0）
4. **「defer 在函数里注册了，函数 panic 了还会执行吗？」**

### 第三幕 · return 的两步与 recover（14 分钟 · L2 · 主战场）

1. **这一份的中心问题，给两段对照的代码**：
   ```go
   func a() int       { x := 1; defer func(){ x++ }(); return x }   // ?
   func b() (r int)   { r  = 1; defer func(){ r++ }(); return r }   // ?
   ```
   —— **`a()` 返回 1，`b()` 返回 2**。
   追：**「为什么只有命名返回值改得动？」**
2. 卡住就提示：**「`return x` 这一行，编译后其实是几步？」**
   —— 要听到：**① 把值赋给返回值变量 ② 执行 defer ③ 真正返回** ——
   **命名返回值就是那个变量本身，所以 defer 改得动。**
3. **「这个特性最常见的正当用法是什么？」**
   （**在 defer 里给命名的 `err` 赋值**，统一包装错误 / 把 panic 转成 error）
4. **recover 部分**：
   ```go
   defer recover()            // 能兜住 panic 吗？
   defer func(){ recover() }()  // 呢？
   ```
   —— **第一个不行**。追：**「为什么必须是『直接在 defer 的函数里调用』？」**
5. **「`recover()` 的返回值是什么？没有 panic 的时候呢？」**
6. **「panic 之后，已经注册的 defer 会不会执行？执行顺序是什么？
   如果 defer 里又 panic 了呢？」**
7. **逼数字**：**「defer 有性能开销吗？1.13 和 1.14 改了什么？
   现在大概多少纳秒？」**
   （堆分配 → 栈分配 → **开放编码（内联），接近直接函数调用**）

### 第四幕 · 逼选型（6 分钟 · L4）

1. **「在一个循环里 `defer file.Close()`，会发生什么？」**
   （**所有 Close 堆到函数返回才执行 → 文件句柄耗尽** →
   追：**「怎么改？」** 用匿名函数包一层或显式 Close）
2. **「你会在哪些地方放 recover？」**
   （**HTTP middleware、每个 goroutine 的顶层、消费消息的循环**）
3. **「哪些 panic 你不该 recover？」**
   （**编程错误** —— 空指针、数组越界、配置缺失这类，
   **让它挂掉比带病运行好**）
4. **「recover 之后，你的程序状态一定是对的吗？」**
   （**不一定** —— 可能锁没释放、数据改了一半）

### 第五幕 · 边界（6 分钟 · L5）

1. **本幕核心一问**：
   ```go
   defer func(){ if r := recover(); r != nil { log.Println(r) } }()
   go func(){ panic("boom") }()
   ```
   **「这个 recover 兜得住吗？」**
   —— **兜不住** —— **panic 只在自己的 goroutine 内展开，
   一个 goroutine panic 会让整个进程退出** ——
   **所以每个 goroutine 都要在自己顶层加 recover。**
2. **「`net/http` 自带了 recover，那是不是就不用管了？」**
   （它只保**当前这个连接的 handler**；**你自己起的 goroutine 它管不着**）
3. **「并发写 map 报的那个错，能 recover 吗？」**
   （**不能** —— **fatal error 不是 panic**，
   还有死锁检测、栈溢出也一样）
4. **「`os.Exit(1)` 之后 defer 会执行吗？」**（**不会**）
5. **「defer 里把返回的 err 覆盖掉，是什么经典 bug？」**
   （`defer f.Close()` 的错误被吞；或者 defer 里给命名 err 赋了 nil）

### 一段合格的 60 秒回答

> defer 在函数返回前执行，**后进先出**。
> 有两个容易错的点：
> **一是参数在注册那一刻就求值了** —— `defer fmt.Println(i)` 打印的是注册时的 i，
> 而写成闭包 `defer func(){ fmt.Println(i) }()` 捕获的是变量本身，打印的是最终值。
> **二是 `return` 其实分三步：先把值赋给返回值变量、再执行 defer、最后才真正返回** ——
> 所以**只有命名返回值能被 defer 改掉**，这也是「在 defer 里统一包装 err」
> 这个惯用法成立的原因。
> recover 只在 **defer 直接调用的那个函数里**有效，包一层就失效，
> 而且**它只能救自己这个 goroutine**：
> **另一个 goroutine panic 了，整个进程还是会挂**，所以每个 goroutine 顶层都要自己兜。
> 还有一类根本救不了：**并发写 map、死锁检测这些是 fatal error，不是 panic。**
> 性能上，1.13 把 defer 改成栈分配、1.14 引入开放编码后基本可以内联，
> **开销已经接近一次普通函数调用**；但**循环里 defer 依然会堆积到函数返回才执行**，
> 打开文件那种场景要用匿名函数包一层。

### L1 · 定义层（必答）

- **执行时机**：函数返回前（包括 panic 展开时），**LIFO**。
- **recover 只在 defer 直接调用的函数体内有效**；
  没有 panic 时返回 `nil`。
- **panic 会执行已注册的 defer**，然后继续向上展开栈。

### L2 · 机制层

1. **参数注册时求值**：
   ```go
   i := 0
   defer fmt.Println(i)          // 打印 0：i 的值此刻被拷进 defer 记录
   defer func(){ print(i) }()    // 打印 10：闭包捕获变量
   i = 10
   ```
2. **`return` 的三步**（这是本题的核心）：
   ```
   return x  ⟹  ① 返回值变量 = x
                ② 执行所有 defer
                ③ 真正返回（RET）
   ```
   - **匿名返回值**：返回值变量是临时的，defer 改的是别的变量 → **改不动**。
   - **命名返回值**：defer 改的就是那个变量 → **改得动**。
3. **recover 必须「直接」调用**：`defer recover()` 无效；
   必须是 `defer func(){ recover() }()`。
   原因：runtime 检查 recover 的调用者是否**正是被 panic 展开的那个 defer 函数**。
4. **defer 的三代实现**：
   **堆分配（≤1.12）→ 栈分配（1.13）→ 开放编码 open-coded（1.14+）**，
   编译器在 defer 数量固定且不在循环里时直接内联到函数尾部。

### L3 · 数字层

| | 值 |
| --- | --- |
| defer 开销（1.12 及之前） | **约 50 ns 量级**（堆分配） |
| defer 开销（1.14+ 开放编码） | **约几纳秒，接近普通函数调用** |
| 开放编码的条件 | **不在循环里、defer 数量 ≤ 8、函数未被 `recover` 复杂化** |
| 循环里 defer | **每次注册都堆积**，直到函数返回才一起执行 |

### L4 · 选择层

- **循环里不要 defer**：
  ```go
  for _, name := range files {
      func() {
          f, _ := os.Open(name)
          defer f.Close()      // 每次迭代结束就关
          // ...
      }()
  }
  ```
- **该放 recover 的地方**：**HTTP/RPC middleware、每个自己起的 goroutine 顶层、
  消息消费循环** —— 目标是「一个请求/一条消息挂掉，不要带走整个进程」。
- **不该 recover 的**：**编程错误**（空指针、越界、类型断言失败、配置缺失）——
  **兜住只会让 bug 更晚被发现**；启动期的错误应该直接退出。
- **recover 之后要当心状态**：锁可能没释放、数据可能改了一半 ——
  所以 recover 通常只用于**隔离单个请求**，不用于「继续正常业务」。

### L5 · 深水区

1. **recover 救不了别的 goroutine（最高频的实战失分点）**：
   panic 只在**自己所在的 goroutine** 展开，
   **任何一个 goroutine panic 且无人 recover，整个进程退出**。
   → **每个 `go func(){}` 都要在顶层自己加 recover。**
2. **`net/http` 自带的 recover 只保当前 handler 的 goroutine**，
   你在 handler 里 `go` 出去的那个它管不了。
3. **fatal error 不是 panic，`recover` 无效**：
   `concurrent map writes`、`all goroutines are asleep - deadlock`、
   栈溢出、`out of memory`。
4. **`os.Exit`（以及 `log.Fatal`）不执行 defer** —— 这是很多「日志没刷出来」的原因。
5. **defer 里再 panic**：原来的 panic 会被记录，最终以最后一个 panic 结束，
   输出里能看到 `panic: ... [recovered]` 之类的链。
6. **defer 吞错误的经典 bug**：`defer f.Close()` 把写文件的 Close 错误丢了 ——
   写文件场景应该 `defer func(){ if e := f.Close(); err == nil { err = e } }()`。

### 常见错答

1. **认为 `defer fmt.Println(i)` 打印的是最终值。**
2. **说不出 `return` 分三步，因此解释不了命名返回值能被修改。**
3. **认为 `defer recover()` 有效。**
4. **认为主函数的 recover 能救别的 goroutine 的 panic**（头号实战失分点）。
5. **在循环里 defer 关闭资源。**
6. **认为所有运行时错误都能 recover**（fatal error 不行）。
7. **不知道 `os.Exit` 不执行 defer。**
8. **无差别 recover，把编程错误也兜住。**
