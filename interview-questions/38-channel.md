### 第二幕 · 代码题（8 分钟 · L1）

**一次一段，问「输出什么/会不会 panic」，不要解释。**

1. ```go
   ch := make(chan int)
   ch <- 1        // ?
   ```
   （**死锁** —— 追：**「为什么？无缓冲不是能放一个吗？」**）
2. ```go
   ch := make(chan int, 2)
   close(ch)
   v, ok := <-ch  // v 和 ok 是什么？
   ```
   （零值 + `false`）
3. ```go
   close(ch)
   close(ch)      // ?
   ch <- 1        // ?
   ```
   （**都 panic** —— 追：**「关闭一个 nil channel 呢？」** 也 panic）
4. **「所以 close 应该由发送方还是接收方做？为什么？」**
5. **「怎么判断一个 channel 已经关闭了？有没有『安全』的检查方法？」**
   （**没有** —— 只能靠 `v, ok := <-ch` 或者约定）

### 第三幕 · 底层与无缓冲的真相（15 分钟 · L2+L3 · 主战场）

1. **这一份的中心问题，直接问：**
   **「无缓冲 channel 是不是就是一个长度为 0 的队列？
   我 `ch <- 1` 的时候，那个 1 放在哪儿了？」**
   —— 要听到：**没有放在任何缓冲区里 —— 发送方直接把值拷贝到
   接收方的栈上（或接收方的变量里），这是一次同步交接（rendezvous）。**
2. **「所以无缓冲 channel 保证了什么？」**（**发送完成 = 接收已经开始**，
   一个天然的同步点）
3. **「`hchan` 结构体里有什么？」**
   —— 要听到：**环形缓冲 `buf`、`sendq`/`recvq` 两个等待队列、
   以及一把 `mutex`。**
   追：**「所以 channel 是无锁的吗？」**（**不是**）
4. **「有缓冲 channel 里，如果此刻正好有一个接收者在 `recvq` 里等着，
   我发送的值会先进缓冲区吗？」**
   （**不会 —— 直接交给等待的接收者，绕过缓冲区**，少一次拷贝）
5. **「一个 goroutine 阻塞在 channel 上的时候，它占着线程吗？」**
   （接 [37-gmp.md](37-gmp.md)：**G 被挂到 waitq，M 继续跑别的 G**）
6. **select 部分**：
   - **「多个 case 同时就绪，select 选哪个？」**（**伪随机** ——
     追：**「为什么不按顺序？」** 防止饿死）
   - **「所有 case 都没就绪、又没有 default，会怎样？」**
   - **「`select {}` 空的会怎样？」**（永久阻塞 → panic: all goroutines asleep）
7. **逼数字**：**「一次 channel 收发大概多少纳秒？和加一次 mutex 比呢？」**

### 第四幕 · 逼选型（7 分钟 · L4）

1. **「什么时候用 channel，什么时候用 mutex？给我一个判据。」**
   —— 要听到：**传递数据/所有权用 channel，保护共享状态用 mutex。**
2. **「缓冲区大小你怎么定？设成 1、设成 100、设成 10000 各意味着什么？」**
   —— 追：**「设大了会掩盖什么问题？」**（**掩盖生产消费速度不匹配**，
   积压在内存里，而且**进程挂了这些数据就没了**）
3. **「超时怎么写？」**（`select` + `time.After` —— 追：
   **「`time.After` 在循环里用有什么问题？」** 每次都新建 timer，1.23 前不会及时回收）
4. **「取消一组 goroutine 用什么？」**（`context` —— 追：**「为什么不用 done channel？
   两者什么关系？」**）

### 第五幕 · 边界（7 分钟 · L5）

1. **「有多个发送者的时候，谁来 close？」**
   —— 要听到：**任何一个发送者 close 都可能让别人 panic** →
   用 `sync.Once`、或者**引入一个额外的 `stopCh` 让发送者自己退出**、
   或者干脆**不 close**（让 GC 回收）。
2. **「nil channel 在 select 里有什么正当用法？」**
   —— **动态禁用某个 case**：把某个 channel 置为 nil，
   它就永远不会就绪，从而「关掉」这一路。**这一问很能筛人。**
3. **「用 channel 写出一个 goroutine 泄漏给我。」**
   （向无人接收的无缓冲 channel 发送；或 `for range ch` 而永远没人 close）
4. **「`for range ch` 什么时候会退出？」**（**close 之后**，
   把剩余元素读完才退出）
5. **「channel 能传指针吗？传了之后所有权算谁的？」**
   （引到 Go 的谚语式原则：**通过通信共享内存，而不是通过共享内存来通信**，
   传了就别再碰）

### 一段合格的 60 秒回答

> channel 底层是 `hchan`：一个**环形缓冲区**、两个等待队列 `sendq` / `recvq`，
> **外加一把互斥锁 —— 所以 channel 不是无锁的**。
> **无缓冲 channel 不是「长度为 0 的队列」，它是一次同步交接**：
> 发送方会阻塞直到有接收方出现，然后**值直接从发送方拷到接收方**，不经过任何缓冲区 ——
> 所以它天然是一个同步点。有缓冲的情况也有个细节：
> **如果此刻正好有接收者在等，发送的值会直接给它、绕过缓冲区。**
> goroutine 阻塞在 channel 上时会被挂到等待队列，**M 可以继续跑别的 G**。
> close 有三条会 panic 的规则：**向已关闭的 channel 发送、重复 close、
> close 一个 nil channel**；而从已关闭的 channel 读是**合法的**，
> 返回零值和 `ok=false`。所以**约定是发送方关闭**；
> 多个发送者时不能随便关，要用 `sync.Once` 或者额外的停止信号。
> select 在多个 case 就绪时是**伪随机**选一个，防止饿死；
> 而 **nil channel 在 select 里永远不就绪，这正好可以用来动态关掉某一路 case。**

### L1 · 定义层（必答）

| 操作 | nil channel | 正常 | **已关闭** |
| --- | --- | --- | --- |
| 发送 | **永久阻塞** | 按规则阻塞/成功 | **panic** |
| 接收 | **永久阻塞** | 按规则阻塞/成功 | **立即返回零值，`ok=false`** |
| close | **panic** | 正常 | **panic（重复关闭）** |

- **约定：由发送方 close**，因为只有发送方知道「没有更多数据了」。
- **没有「安全检查是否已关闭」的 API** —— 只能靠 `v, ok := <-ch` 或设计约定。

### L2 · 机制层

- **`hchan` 结构**：`buf`（环形缓冲）、`sendx`/`recvx`（读写下标）、
  `sendq`/`recvq`（等待的 goroutine 队列 `sudog`）、**`lock mutex`**。
- **无缓冲 = 同步交接（rendezvous）**：
  发送方找不到接收者就把自己挂进 `sendq` 并让出；
  接收者到来时**直接把值从发送方拷到接收方**，然后唤醒发送方。
  **值从不经过缓冲区。**
- **有缓冲的快捷路径**：发送时若 `recvq` 非空，**直接交给等待的接收者**，
  绕过缓冲区（少一次拷贝）。
- **阻塞的代价很低**：G 挂到等待队列并让出 P，**M 继续跑别的 G**（见 [37-gmp.md](37-gmp.md)）。
- **select**：编译成 `selectgo`；**对就绪的 case 做伪随机选择**（防饿死）；
  有 `default` 则变成非阻塞；**所有 case 都是 nil 且无 default → 永久阻塞**。

### L3 · 数字层

| | 量级 |
| --- | --- |
| 一次 channel 收发（无竞争） | **约几十~上百 ns**（含一次加解锁） |
| 一次 `sync.Mutex` 加解锁（无竞争） | **约 20 ns** |
| 阻塞/唤醒一个 G | **几百 ns**（用户态，不进内核） |
| 缓冲大小 | **通常 0、1 或与并发度同阶**；设很大等于把队列藏进内存 |

**推论**：**channel 比 mutex 贵**，在「只是保护一个计数器」这种场景
用 mutex/atomic 更合适。

### L4 · 选择层

- **判据**：**传递数据或所有权 → channel；保护共享状态 → mutex。**
  （`sync.Mutex` 保护一个 map 比用 channel 串行化访问简单得多，也快得多。）
- **缓冲大小**：
  - **0**：要求同步交接，天然背压
  - **1**：解耦一次，常用于信号
  - **很大**：**掩盖生产/消费速率不匹配**，把问题变成内存占用，
    而且**进程退出时缓冲里的数据全部丢失**
- **超时**：`select { case v := <-ch: ... case <-time.After(d): ... }`；
  **循环里用 `time.After` 会不断创建 timer**（Go 1.23 前不会提前回收），
  高频场景用 `time.NewTimer` + `Reset`。
- **取消**：**用 `context`**，它本质上就是一个带层级传播的 done channel +
  截止时间；自己造 done channel 只在简单场景够用。

### L5 · 深水区

1. **多发送者时谁来 close**：**任何一方 close 都可能让其他发送者 panic**。
   三种做法：① `sync.Once` 保证只关一次，且发送前检查停止信号
   ② 引入 `stopCh`，让发送者自己退出、**不关数据 channel**
   ③ **干脆不 close** —— channel 会被 GC 回收，close 只是给接收方的信号。
2. **nil channel 的正当用法**：在 `select` 中把某个 case 的 channel 置为 `nil`，
   **该分支永远不会被选中** —— 用来「动态关闭」一路输入
   （例如上游关闭后不再监听它，避免 `for range` 空转）。
3. **goroutine 泄漏的经典形状**：
   ```go
   ch := make(chan int)      // 无缓冲
   go func() { ch <- compute() }()   // 没人接收 → 这个 goroutine 永远卡住
   return                            // 调用方提前返回了
   ```
   **修法**：给 channel 加缓冲 1，或者用 `select` + `ctx.Done()`。
4. **`for range ch` 只有在 close 之后才会退出**（并且会先读完缓冲里剩下的）。
5. **channel 传指针后要放弃所有权**：否则就退回到共享内存，
   还得自己加锁 —— 违背「通过通信共享内存」的初衷。
6. **`close` 是广播**：所有阻塞在接收上的 goroutine 都会被唤醒 ——
   这是实现「一对多通知」的标准手法（done channel）。

### 常见错答

1. **把无缓冲 channel 说成「长度为 0 的队列」**，讲不出同步交接（头号失分点）。
2. **认为 channel 是无锁实现。**
3. **不知道 close 的三种 panic 情形。**
4. **认为「关闭后就不能读」。**
5. **多发送者时随手 close。**
6. **不知道 nil channel 在 select 里的用法。**
7. **认为 channel 总是优于 mutex。**
8. **写不出 goroutine 泄漏的例子。**
